## 我认为有争议的取舍

1. **§8 整表删除，赌 `mem.py search` 的召回**。这张 42 行表是人工维护的高质量映射，删掉后新会话第一次找文件完全依赖检索质量。建议等任务 10/20 的检索评测数据出来再拍板；如果 `search` 在改写问法下的命中率不达标，§8 应保留一个 ≤10 行的精简版（只留最高频主题）。
2. **4,000 字是硬卡线，压出了信息损失**。为了卡住上限，§5 砍到 7 条、§6 砍到 7 条，`deployService 只部第一个词`、`夸克 41031`、`sweep-guard 已合并` 等 16 条直接删出总览。这些在详细文件里都有，但**总览失去了"不检索也知道有这回事"的提示作用**。如果 AGENTS.md 的「复杂项目 ≤4000 字」允许按字符外的口径算（比如按 token 或按中文字数），实际可放宽到 ~5,500 字符，§5/§6 能各回到 10 条。建议向用户确认「字数」的口径。
3. **P4 bootstrap 从 4 行滚动记录压成 2 行**。这是当前唯一的长周期生产作业，原文那 4 行里混着大量只有巡检 Agent 才用得上的细节（轮次、容器 id、md5、回滚位）。草案把它们全部推给 `current/tasks.md`，代价是：接管巡检的新会话必须多读一次 `current/tasks.md`（9.1 万字符，本身也超标）。**建议把 §2 的 P4 条与 `current/tasks.md` 的瘦身放在同一轮做**，否则只是把膨胀从总览挪到了 tasks。
4. **`changelog.md` 保留原文而不做二次压缩**。14,066 字符且内容与 `sessions/` 高度重叠（估计重复率 >60%，可用 `mem.py dup` 量化）。选择原文保留是为了"证明没有信息丢失"，但长期看它应该被压成"日期 + 一句话 + session 路径"的索引，否则是第三份副本。
5. **§2 的「最近 7 天」是滚动窗口，需要有人维护**。规则好写，但没人跑就会退化成"永远不删"。建议配合 `mem.py recent --days 7`（已有子命令）在会话收尾时自动核对，而不是靠约定。
