# 结果 10：检索方案对比（mem.py search）

工具：`scripts/mem/bench/search_bench.py`（直接 import `mem.py`，不 subprocess 逐条跑；按「jieba 开关 / 语义模型 / 切块大小」分组复用词法与语义打分，RRF 融合参数在同一组打分结果上重算，近乎零成本）。
候选文档：98 篇（101 篇总数排除 `load: always` 的 3 篇常驻文件）。
评测集：`gold.jsonl`（41 topic / 167 query，原始问法，对 `01-index.md` 泄露）+ `gold_paraphrased.jsonl`（41 topic / 123 query，改写问法，跨方案比较以此为准）。
指标：对每条 query 单独算 Hit@1/3/5（命中=结果落在该 topic 的 expected 集合任意一个文件）与 MRR，再对该 gold 文件内所有 query 取平均。
环境：本机 32 核 CPU，无 GPU；jieba/fastembed/numpy 已装；模型缓存于 `~/.cache/fastembed`（bge-small-zh ~90MB、jina-v2-base-zh ~640MB、bge-m3 ~2.27GB，磁盘 174G 可用，无压力）。bge-m3 fastembed 0.8.0 未内置，用 `TextEmbedding.add_custom_model` 挂载 `BAAI/bge-m3` 仓库自带的 onnx 权重后可用（已固化进 `mem.py` 的 `register_custom_embed_models()`，仅在非默认模型时触发，不影响默认路径）。

## mem.py 改动说明（保持默认行为不变）

- `_chunks_of/_embedder/semantic_index` 新增 `model_name`/`chunk_chars` 参数；非默认组合使用独立缓存文件（`embeddings__<模型>__<chunk>.pkl`），默认组合仍写 `embeddings.pkl`，与改动前完全兼容。
- 新增 `register_custom_embed_models()`：仅当请求的模型不是默认 `bge-small-zh` 时才尝试给 fastembed 注册 `BAAI/bge-m3`，默认路径不触碰。
- 抽出 `fuse_scores(lex, sem, by, mode, K, sem_weight, min_sim, boost)`：把原来写死在 `cmd_search` 里的 RRF 融合逻辑变成可复用函数，`cmd_search` 行为不变（默认 `K=30, sem_weight=1.3, min_sim=0.35, boost=True`），bench 脚本靠它扫参数。
- `_doc_boost` 新增 `enable` 开关，默认 `True`（不变）。
- 未新增任何子命令，`search` 的 CLI 参数/默认值均未变，回归验证：`mem.py search 代理池 无数据 -q` 结果与改动前一致。

## 结论

1. **换语义模型是唯一有实质收益的改动**：hybrid + `jina-embeddings-v2-base-zh` 在改写问法上 Hit@1 从 0.593→0.675（+8.2pp）、Hit@5 从 0.846→0.894（+4.8pp）、MRR 0.702→0.769，原始问法上同样全面提升。bge-m3 精度与 jina 基本打平（部分指标甚至更低），但建索引慢 2.9×、单次查询语义打分慢 1.7×（29.7ms vs 17.1ms，量级都很小但差距明显）、模型体积大 3.5×——**没有理由为 bge-m3 买单，建议换成本更低的 jina-v2-base-zh**。
2. **RRF 融合参数（语义权重/K/min_sim）已接近当前语料的最优点**：扫的所有替代值都不优于现有默认（w=1.3, K=30, min_sim=0.35），无需改常量。换模型后若要精调可再扫一轮，但本轮数据不支持现在就改。
3. **切块大小 600 字优于 300/1200**：两侧改写问法都不如默认，300/1200 均无提升，维持 `CHUNK_CHARS=600`。
4. **文档 boost 利大于弊**：关掉后原始问法 Hit@1 掉 5.4pp（0.617→0.563），改写问法小幅升 0.9pp 但 Hit@5 反而掉 1.7pp——净效果是开着更好，维持现状。
5. **jieba 对词法检索没有显著优势，反而慢 4 倍**：bigram 与 jieba 在两个 gold 集上 Hit@1/3/5/MRR 互有胜负、差距在 1-2pp 内（噪声量级），但 jieba 每次查询要 200ms（对全语料 body 字段重新分词），bigram 只要 47ms。**如果延迟敏感，禁用 jieba 也不会掉点**；如果不敏感，装不装都行（这点不建议改默认行为，只是澄清 README 里"jieba 分词质量更好"的说法在当前语料上未被数据支持，值得记一笔留待更大语料再验证）。
6. **语义单独用远不如混合**：semantic-only 在三个模型上都明显弱于对应的 hybrid（例如 bge-small-zh 语义单独 Hit@1 仅 0.439~0.473，混合后 0.593~0.617），说明专有名词/站点代号（haisou、kkpans、res_lc 等）词法匹配仍是刚需，语义解决不了这类精确术语召回，融合架构本身是对的，不建议改成纯语义检索。
7. **延迟瓶颈是词法而不是语义**：语义打分（含模型换成 bge-m3）每次查询最多 30ms，可忽略；真正拖慢单次查询的是词法阶段（jieba 开时 ~200ms），根源是 `mem.py` 每次进程都要对全部 98 篇文档的 5 个字段重新分词（无跨调用缓存）。这是 CLI 单次执行模型的固有成本，不在本次任务范围内改，但如果以后要继续优化延迟，方向是词法侧缓存而不是纠结语义模型选型。

**建议默认配置**：`mode=hybrid, EMBED_MODEL=jinaai/jina-embeddings-v2-base-zh, CHUNK_CHARS=600, K=30, sem_weight=1.3, min_sim=0.35, boost=on`（除模型换掉，其余全部维持现有默认）。换模型的代价是一次性重建索引 ~180s（增量场景下只对变更文件重算，可忽略）+ 模型缓存从 90MB 增至 640MB，磁盘/耗时都不是问题，收益（尤其改写问法上的 Hit@1/Hit@5）明显，**值得换**；bge-m3 则不值得（同等精度、更贵）。

## 失败案例分析（改写问法下 hybrid-default 未命中 Hit@5 的 topic，按错误条数排序取前 5）

1. **`后台怎么看 res_lc_* 分表数据`**（3/3 条改写 query 全错，expected: `sessions/2026/2026-09-08-res_lc数据纳入后台.md`）
   问法都在问"分表列表/汇总统计页面能力"，结果被 `architecture-nc-js`、`architecture-es索引现状` 等泛化架构文件抢占。根因是**双重的**：a) 期望文件是 `sessions/`，被 boost 结构性降权（×0.7），和"会话性价比低"的设计意图冲突——这份 09-08 的会话记录实际上承载着别处没有的知识点（后台分表能力），不是普通流水账；b) 该 session 文件的 Front Matter 关键词大概率只覆盖了 `res_lc`/`分表` 这类精确代号，没覆盖"列表"、"汇总统计"、"事件流水"这类改写后的通用说法。
   建议：若这块知识长期有价值，应该按决策文件里"防复发"的思路搬进 `knowledge/`（不受 sessions 降权影响）；若暂不搬，至少给该 session 文件补 `questions:` 字段（如"后台怎么查分表数据"、"资源列表和汇总统计在哪看"），因为 `questions` 字段在词法打分里权重等同 `keywords`（6.0）。**不是 gold 期望不合理，是文件元数据/归档位置的问题。**

2. **`新增服务配置节 / yaml 解析 Duration / 线上配置没同步`**（2 条错，expected: `knowledge/architecture-spider.md`）
   改写后的问法（"新服务加配置项格式上要注意什么"、"新增配置项怎么保证线上同步"）都被两篇 `decisions/` 配置拆分决策文档抢走，这两篇决策讲的是"配置该不该按进程拆"，跟"具体怎么给新服务写配置节/yaml Duration 解析"是不同粒度的问题。说明 `architecture-spider.md` 的 `keywords`/`summary` 里大概率没有覆盖"新增服务配置""yaml 解析""线上配置同步"这几个说法，而决策文件的 `keywords` 里有大量"配置"相关词汇，词法分数占优。
   建议：给 `architecture-spider.md` 补充 `keywords`/`questions`（"新增服务配置怎么写""yaml Duration 怎么解析""改完配置怎么保证线上同步"），或者在 `summary` 里显式提一句"新服务配置节写法"。**是文件元数据覆盖不够，不是 gold 不合理。**

3. **`我要改入库逻辑 / ES 索引 / 查资源为什么没写进去`**（2 条错，expected: `knowledge/architecture-storage.md`）
   改写问法（"入库接口返回成功但查不到数据""资源入库那部分逻辑流程"）命中的是各种 `lessons/failure-*` 和别的 workflow 文件，没有一条命中期望的架构文件。同样是关键词覆盖问题：用户会用"入库逻辑""写不进去""查不到"这类症状级描述提问，如果 `architecture-storage.md` 的 Front Matter 只写了"存储架构"这类抽象词，就接不住这种症状式问法。
   建议：给该文件补 `questions:`（如"入库接口成功但查不到数据是为什么""资源入库逻辑是怎样的"），把症状级问法预先接进关键词索引。

4. **`当前该做什么`**（2 条错，expected: `current/open-questions.md` + `current/tasks.md`）
   改写问法是纯元问题（"手头还有什么事没干完""接着上次会话往下做"），完全不含领域词汇，词法和语义都没有锚点可抓，结果落到了一堆 `lessons/failure-*`（这些文件因为词汇丰富、body 很长，反而在没有强信号时靠字数堆分数占了便宜）。
   这是**gold 期望本身不太适合用"检索"解决**的例子：一个通用元问题不应该依赖搜索命中特定文件，而应该是 AGENTS.md 启动协议里就规定"任何会话开始固定读 current/tasks.md + current/open-questions.md"，属于协议兜底，不是靠关键词/语义能覆盖的场景。建议在决策落地时，把这类 topic 从"检索基准"里移出（或标注"仅供参考，不计入达标线"），改成走固定加载协议验证。

5. **`配置怎么读 / 某个进程读哪些配置 / config.Config 去哪了`**（1/4 条错，expected: `decisions/decision-2026-09-09-配置按进程拆代码而非文件.md`）
   唯一错的一条是纯代码报错描述（"config.Config 这个类型找不到了，编译报错说没有这个定义"），不带"配置""网关"这类高权重词，落到了几篇不相关的 `lessons/failure-*`。这条从原始 4 条问法看整体覆盖已经很好，只是这一种"编译报错"的极端症状级说法没接住。
   建议：给该决策文件的 `questions:` 加一条"config.Config 类型找不到了/编译报错说没有这个类型"，属于低成本的关键词补漏，优先级低于前三条（整体命中率已经不错）。

**汇总建议**：5 个失败 topic 里，3 个（#2 #3 #5）是纯粹的 Front Matter 关键词/`questions` 覆盖不足，修复成本低（补几行 `keywords`/`questions`）；1 个（#1）是内容该不该待在 `sessions/`（受结构性降权拖累）的归档位置问题；1 个（#4）是 gold 期望把"协议兜底类"元问题也算进检索基准，建议后续单独标注或移出。**没有发现"检索算法本身有明显缺陷"导致的失败**——换成 jina 模型后（见结论 1）整体命中率已有提升，可能已部分覆盖这类语义泛化不足的情况，值得在换模型后重新跑一次这 5 个 topic 验证是否好转（本轮未针对性复核，可作为后续快速验证项）。
