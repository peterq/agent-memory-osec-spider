## N1. proto3 零值陷阱：三个字段的"不过滤"哨兵不是 0（前端必须处理）

> 来源：后端实现方 2026-09-08 汇报。**主控确认这是真实缺陷来源，前端按此处理。**

`ListResourcesParam` 里有三个字段的合法取值**从 0 开始**，而 proto3 字段不显式赋值时零值也是 0：

| 字段 | "不过滤"的哨兵 | 不传时的零值 0 会被当成 |
|---|---|---|
| `indexRole` | `-1` | `0` = 只看 legacy 索引 |
| `lastCheckResult` | `-1` | `0` = 只看从未检测过的 |
| `bucket` | `-1` | `0` = 只查 0 号分表（而非全部 16 槽） |

后果：前端忘记显式传 `-1` 时，不会报错，而是**静默返回被意外收窄的结果**（大概率是空列表），
排查起来很费时间。

**前端必须做的**：这三个字段在筛选表单的 state 初始值、以及"重置筛选"的复位值，都要显式设成
`-1`，不能依赖"不填"。发请求时也要保证这三个字段总是被显式赋值。

对照：`status` / `minFailCount` 没有这个问题——它们的"不过滤"哨兵正好就是 0。
后端已按契约字面实现，并写了专门的测试用例固化这个行为，**不要指望后端兜底**。

## N2. 后端已完成，实现侧的既成事实（前端据此对齐）

- `maxOffset = 10000`，`ListResources` 与 `ListEvents` 共用。
- `limit` 缺省 50，服务端夹到 1..200。
- `TableStats` 只有在 `exact=true` 时才做维度 `GROUP BY` 与到期积压统计。
  也就是说 **`exact=false` 时 `dims` 与 `dueBacklog` 都拿不到数**（`dueBacklog` 为 `-1`）——
  前端在估算模式下要把维度分布区域显示成「需开启精确统计」，而不是渲染成空图表。

  口径写在响应的 `note` 字段里——前端要把 `note` 显示出来，别让人以为 diff 是实时精确的。
- `ListEvents` 在 `resId` 为空时 `fromMs` 必填，后端会报错（与 `20-frontend.md` 的前端校验要求一致）。

## N3. `dueOnly` 口径裁定：实现正确，注释待补，但组合筛选会静默返回空

> 来源：前端实现方 2026-09-08 提出「`dueOnly` 与 `withDueBacklog` 口径可能不一致」。
> 主控核实后裁定如下。

**核实结果**：三处口径其实是**一致**的，后端 `browse.go` 已实现为
`status = 1 AND next_check_at <= now`，与 `dao.go` 的 `ScanDue`（扫描器取到期行的真实口径，
走 `idx_due` 复合索引 `(status, next_check_at)`）以及 `TableStatsParam.withDueBacklog` 相同。
问题只出在 **proto 注释漏写了 `status=1`**，不是实现缺陷。

**裁定**：
1. 后端实现**保持不变**，是对的。
2. `lifecycle.proto` 里 `dueOnly` 的注释要补全为「`status=1 且 next_check_at<=now`，
   口径与 `ScanDue` / `withDueBacklog` 一致」。**由主控在验收结束后统一改**，避免与验收
   并发改动生成代码（改注释要重跑 `gen.sh`，会产生大片 pb.go diff）。
3. **新暴露的问题（需要前端处理）**：`status` 与 `dueOnly` 是两个独立筛选条件，用户若同时选
   `status=失效/已删除` + 勾选「只看到期」，SQL 会拼成 `status=2 AND … AND status=1 AND …`，
   **恒为空结果且不报错**，用户会困惑于"明明有数据却查不出来"。
   前端要做防呆：勾选「只看到期」时把 status 锁定/自动切到「有效」并给出说明，
   或在 status 非「有效」时禁用该勾选项。二选一，实现方自行判断哪种更顺手。
