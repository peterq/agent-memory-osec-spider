# 失败经验：proto3 零值与 -1 哨兵冲突

## 问题背景

2026-09-08 设计 `ListResourcesParam`（res_lc_* 分表列表查询）时，给几个枚举筛选字段定的
「不过滤」哨兵是 `-1`：

| 字段 | 哨兵 | 但 0 也是合法业务值 |
|---|---|---|
| `indexRole` | `-1` | `0` = legacy（仅旧索引） |
| `lastCheckResult` | `-1` | `0` = 从未检测 |
| `bucket` | `-1` | `0` = 0 号分表 |

## 失败表现

proto3 的标量字段**不显式赋值时零值就是 0**，且无法区分"没传"和"传了 0"。
于是前端漏传这三个字段时，请求不会报错，而是被静默解释成
「只看 legacy 索引 + 只看从未检测过的 + 只查 0 号分表」——返回一个**被意外收窄、
通常为空**的结果集。用户看到的是"明明有数据却查不出来"，排查要翻到后端 SQL 才能定位。

对照：同一个消息里的 `status` / `minFailCount` **没有**这个问题，因为它们的
「不过滤」哨兵正好就是 0。同一份契约里两套相反的约定，更容易记错。

## 根本原因

把「不过滤」这个**带外语义**塞进了值域本身，而该值域的 0 已经被业务占用。
proto3 又没有 presence 语义（不像 proto2 的 `optional` 或 `wrappers.Int32Value`），
`0` 在服务端无从判断是"用户选了 legacy"还是"用户什么都没选"。

## 规避方法

按优先级：

1. **让哨兵落在值域之外**：业务值从 0 开始时，「不过滤」用 `-1`；
   业务值从 1 开始时（如 `status`），直接用 `0`。**同一个消息里两种都出现时，
   必须在每个字段的注释里逐个写清**，不能只在消息顶部写一句通则。
2. 更彻底的做法：用 `optional`（proto3 field presence）或包一层 message，
   让"没传"与"传了 0"在服务端可区分。本次未采用，因为改动面波及已上线的生成代码。
3. **前端侧强制显式赋值**：表单 state 初始值、"重置筛选"复位值、构造请求参数处，
   三个地方都要显式写 `-1`，不能依赖"不填"。
4. 服务端加一条**固化该行为的单元测试**，避免后来者"顺手改成 0 更自然"。

## 下次行动建议

设计筛选类 proto 消息时，逐个字段自问一句：**「这个字段的 0 是合法业务值吗？」**
是，就不能让 0 承担"不过滤"；同时确认前端有没有可能漏传。
契约评审时这是必查项——它不报错，只静默给错数据，是最难排查的一类缺陷。

## 适用边界

任何 proto3 标量筛选参数；gRPC / protobuf-ts 前后端均适用。
JSON API 无此问题（`undefined` 与 `0` 可区分），但同样要防"前端传了 0 当没传"。

## 本次如何被发现

**不是**测试发现的，是后端实现方按字面实现后**主动在汇报里提示前端注意**。
主控把它写进 `agent-tasks/…/99-notes.md` 的 N1 转给前端，前端核实后确认已落实。
经验：跨端契约陷阱靠单侧测试测不出来（两侧各自都"符合契约"），
**要靠实现方主动上报 + 主控在两端之间做一次对齐**。
