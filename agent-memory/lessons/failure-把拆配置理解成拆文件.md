# 失败经验：把"配置按服务拆分"理解成拆配置文件

## 问题背景

用户一句"配置按服务拆分"，09-08 会话直接落成了"网关/爬虫两份 YAML + deploy.sh 按命令选文件 +
运行时断言防网关误连自己"，写了脚本、runbook、两层回滚方案，共 4 个文件 400 多行文档。

## 失败表现

用户次日指出：要的是拆**代码**（每进程自己的配置结构体、`GetXXX()` 惰性初始化、禁止全局
`config.Config`），文件反而要保持一份。整套文件拆分方案作废回退。

## 根本原因

1. **没有复述"拆分的对象"**。"拆分"可以指代码结构、文件、进程、部署单元，会话选了最省事的一种
   （改脚本不改代码）没有确认。
2. **用错误层级的手段去兜隔离**：加运行时断言 `MarkCurrentProcessAsGateway`、在文件里"不写某项"
   来避免自动注入——这两样都是在数据/运行时层修补一个**类型层**的问题。当你发现自己在写
   "如果误用就 panic"的护栏时，说明本可以让误用根本编译不过。
3. 做完自查"全仓 grep 确认网关不读这些字段"看起来很严谨，但那是在验证一个错误方案的自洽性。

## 规避方法

- 收到"拆分/隔离/解耦"类需求，先用一句话复述：**拆的是什么、边界在哪、靠什么保证**，
  再动手。这类需求改动面大，复述成本远低于返工。
- 隔离需求优先问"能不能让错误的引用编译不过"（类型、package、构建 tag），
  其次才是运行时断言，最后才是数据/配置层的绕行。
- 方案里出现"为了保证 X，配置文件里不要写 Y"这种说法，就是层级选错的信号。

## 适用边界

适用于所有结构性重构需求；不适用于用户已经给出明确文件级操作指令的场景。
