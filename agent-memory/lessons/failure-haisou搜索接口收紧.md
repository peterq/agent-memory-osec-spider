# 失败经验：haisou.cc 搜索接口在调研当天被收紧

## 问题背景

2026-09-03 上午的站点发现任务判定 `haisou.cc` **满足**全部验收标准：
逆向出公开接口 `POST /api/v2/shares/search`，免登录直出真实分享码，
串行 20 次全部成功，94 条抽样有效率 88.37%，唯一卡点是每日约 50 次的匿名额度（业务码 `11003`）。

同日下午按该报告开发 `keyword_haisou` 爬虫时，**核心搜索接口再也没拿到过一次成功响应**。

## 失败表现

- `POST /api/v2/shares/search` 稳定返回 HTTP 429 + 业务码
  `13001`「请求过于频繁」。
- **上午的调研报告里从未出现过 `13001`**——这是当天新出现的行为，不是我们没读报告。
- 关键鉴别实验（三次独立验证，含主会话亲自复核）：
  | 观察 | 结果 | 含义 |
  |---|---|---|
  | 同一代理请求首页 | HTTP 200 | 站点是活的，不是宕机 |
  | 其余接口（configs / stats / 热搜词） | 全程 200，热搜词接口拿到 50 个真实关键词 | 限流精确定位在 `shares/search` 单一端点 |
  | **全新代理 IP 的第一次**搜索请求 | 立刻 429 | **不是我们把该 IP 的配额跑光了** |
  | 间隔 20+ 分钟后重试 | 仍 429 | 冷却窗口远超站方声明的 `search_free_limit=5/60s` |
  | 首页响应的 Set-Cookie | 无 | 不是缺会话 cookie |
  | 入口 JS bundle（191KB）搜自定义头/签名/nonce/token | 零命中 | 不是缺客户端计算的签名头 |

## 根本原因（[推断]，未能证实）

最可能是站点在上午那轮调研流量之后收紧了搜索端点的风控，
或对代理商（蜻蜓）的网段做了整段封禁。
（⚠️ 此处当时写的「蜻蜓＝机房 IP」是**错的**，见文末「更正」一节。）

**无法做的那个决定性实验**：从非代理的本机 IP 试一次即可区分
「代理网段被封」与「站点全局收紧」。但这违反项目硬规则
「分享链接爬虫一律走代理池」，且会烧掉办公出口 IP，**故意没做**。
这个取舍本身是对的——不要为了一个诊断结论去赌一个影响面更大的资源。

## 教训

1. **调研结论有保质期，尤其是"限流/配额"这一类**。规模、有效率、字段结构相对稳定，
   但反爬策略可能在**同一天内**变化。站点发现与爬虫开发间隔越久，越要在动手前
   花一次请求重新验一下核心接口还通不通，别等写完代码才发现验收不了。
2. **调研阶段的探测流量本身可能触发站点收紧**。上午跑满 50 次配额去测额度边界，
   很可能就是下午被针对的原因。探测"额度上限在哪"的收益，要和"把站点惹毛"的代价一起算。
3. **区分"配额耗尽"与"端点级封禁"要靠全新 IP 的首次请求**。
   新 IP 首请求就被拒 ⇒ 与我们的历史用量无关，是策略变了。这个判据很便宜也很硬。
4. 排查这类问题的顺序（从便宜到贵）：换 IP → 换端点对照 → 看 Set-Cookie → 翻 bundle 找签名头。
   四步都排除了，才轮到"站点针对性封禁"这个结论。

## 下次行动建议

- 若要重新启用 haisou：先用一个**没用过的代理 IP** 发单次搜索请求探路，
  通了再谈规模化；连续几天不通就要考虑换代理来源（不是换成住宅代理——现在用的就已经是住宅宽带）。
- `keyword_haisou` 的代码已合并进 master，离线单测通过、结构完整，
  **但从未有过一条真实入库数据**，上线前必须补联网验收。

## 适用边界

适用于所有"调研与开发分离、且中间隔了一段时间"的站点接入。
站点越是有明确的风控产品设计（积分/额度/会员），越适用。

## 追加：2026-09-03 傍晚的第二轮归因（更硬的结论）

用户人工调研发现该站有一套明确的积分产品设计，并据此提出方案：
「把 IP 积分余额存 redis（过期到 24:00），OnProxy 时余额 <5 直接过滤该 IP，调接口后扣减」。

按此方案动手前先验证前提，结果**前提不成立**，方案解决的不是当前的阻塞。

### 实验与结论

全部实验都在**刚从代理池推出来的全新 IP** 上做，每个 IP 只发一次搜索请求，互不污染。

| 实验 | 结果 | 排除了什么 |
|---|---|---|
| 全新代理 IP 查 `/api/v2/credits/membership/status` | 200，`remaining_today=100`、`used_today=0` | 站点确实认这些 IP，且额度**满格未动用** |
| 同 IP 紧接着搜索 | 429 / `13001`，事后再查额度**仍是 100/0** | **13001 与积分无关**，请求根本没走到扣分那一层 |
| 完整浏览器请求头（Origin/Referer/sec-ch-*） | 仍 13001 | 不是缺请求头 |
| 先 GET 首页建会话再搜索（首页 200，**无 Set-Cookie**） | 仍 13001 | 不是缺会话/cookie |
| `curl --http2`（HTTP/2 + 另一套 TLS 栈） | 仍 13001 | 不是 HTTP 版本 / 客户端栈 |
| 带 `X-HS-Client-Context` 头（见下） | 仍 13001，**积分仍未扣** | 不是匿名身份识别 |
| `/`、`/api/v2/common/configs`、`credits/membership/status` | 全程 200 | 站点是活的，拦截**只针对 `shares/search` 端点** |

**结论 [推断，证据充分]**：13001 是**积分层之前**的一道按来源网络生效的端点级拦截，
代理池（蜻蜓）的 IP 段整段被针对。改客户端行为（头、指纹、节流、积分账本）都绕不开。

### 附带的重要发现：站点新增了匿名身份机制

从首页最大的 JS chunk（搜 `hs:anonymous:visitor-id`）逆向出：

- FingerprintJS 算 `visitorId`（32 位十六进制）存 localStorage；
- 每个 API 请求带 `X-HS-Client-Context` 头 = base64(RSA-OAEP/SHA-256 加密的
  `{"v":1,"id":visitorId,"ts":毫秒,"n":uuid,"ua":sha256(UA)}`)；
- RSA 公钥（2048 bit / SPKI DER 294 字节）在 bundle 里被拆 7 段 base64 + 乱序 +
  xorshift32(seed=1141874173) 异或混淆。

已复刻并**验证服务端采信**：`anonymous_identity_type` 从 `ip_fallback` 变成 `client_context`。
实现在 `osec-spider-go/scripts/haisou_client_context.py`（带自检），
`scripts/haisou_probe.py` 已接入并新增 `credits` 子命令（不耗积分，最便宜的连通性探针）。

⚠️ 2026-09-03 上午那轮调研**没有**这个头也能搜到东西，说明该机制是当天新上的；
现有 Go 爬虫 `services/haisou/haisou.cc.go` **不带这个头**，恢复访问后必须补上。

### 积分模型（事实，已实测）

`/api/v2/common/configs` + `credits/membership/status` 一致给出：

- 游客每日 100 积分，`search`=2 / `check_share`=1 / `fetch_share`=5；
- `anonymous_buckets` 有**两个**桶：`ip` 与 `fingerprint`，各 100，实际额度取两者更小的那个。
  → 所以用户提的「按 IP 记账」方向是对的（IP 桶是真实约束），
  visitorId 应当**按代理 IP 固定复用**，换 visitorId 拿不到超过 IP 桶的额度。

### 教训（在原有 4 条之上）

5. **动手实现一个"配额管理"方案之前，先花一次请求确认阻塞真的是配额。**
   本次用户方案的每一条描述都与站点文档吻合，但当前的 429 根本没走到配额层——
   判据只要一个：**全新满额 IP 的首次请求是否也被拒、事后额度是否被扣**。
6. **排查这类拦截时，"哪些端点还通"比"这个端点怎么调都不通"信息量大得多。**
   同一 IP 上 status/configs/首页全 200、只有 search 429，一步就把范围从
   "IP 被封"收敛到"端点级针对"。
7. 逆向前端找的**不只是签名头**：`anonymous_identity_type` 这类**响应字段**会直接
   点出站点在用什么身份维度，顺着字段名去 bundle 里搜，比盲搜 `sign/token/nonce` 准得多。

### 已落地的代码（2026-09-03 傍晚，SPIDER 未提交）

用户确认「连积分账本一起写」，已实现并编译/单测通过（**联网仍无法验收**，因为 13001 未解除）：

| 文件 | 内容 |
|---|---|
| `services/haisou/client_context.go` | Go 版身份头：还原混淆公钥 + RSA-OAEP 加密 payload |
| `services/haisou/credits.go` | 积分账本 + 代理准入闸门 + status 拉取 + `BeforeSend` 头装配 |
| `services/haisou/credits_test.go` | 离线单测：公钥还原、头不可重复、IP 提取、次日零点 TTL（含 UTC 输入与 23:59:59 边界） |
| `config/config.go` | `minCredits` / `creditsRefreshInterval` / `visitorIdTTL` 三个新字段，全部有内置缺省 |
| `scripts/haisou_client_context.py`、`scripts/haisou_probe.py` | Python 版身份头 + `credits` / `curl` 两个新子命令 |

设计要点（与用户原方案的差异都在这）：

- **账本按 IP 记，不按 `ip:port`**：代理商给同一出口 IP 分不同端口，按 ip:port 会把同一份额度重复算。
- **TTL 到次日零点（东八区）**，且 `DECRBY` 后要补一次 `Expire`——跨零点时键已过期，
  DECRBY 会建出一个**没有 TTL 的负数键**，会把该 IP 永久拉黑。
- **status 刷新做了节流**（默认 30 分钟一个 IP，靠一个短 TTL 标记键）。
  用户原方案是"每次 OnProxy 都刷新"，但代理池会持续复推同一批 IP、代理 leader 只活 5 分钟，
  不节流会变成每 IP 每几秒一次真实请求。账本在两次刷新之间靠本地扣减维持。
- **扣多少以站点回传的 `meta.credits_consumed` 为准**，缺失才按常量 2 兜底，站点调价能自动跟上。
- **visitorId 按代理 IP 绑定并存 redis**（`haisou:vid:<ip>`）：额度是 ip 桶与 fingerprint 桶取小，
  换指纹拿不到更多额度，反而让同一 IP 上出现大量一次性指纹，特征更明显。
- 身份头挂在 `proxy_client.Request.BeforeSend` 上，因为它必须和**实际派发到的那个代理**绑定，
  而代理是调度时才确定的。
- `fetchCredits` 顺带校验 `anonymous_identity_type`，不是 `client_context` 就告警——
  站点换公钥时服务端不报错、只是把身份退回按 IP 识别，这是唯一能及时发现的判据。

### 结论定案（2026-09-03 晚，用户实测补齐最后一块）

用户在自己的 IP 上把当日 100 积分**用光**，补齐了此前缺的那个决定性观察：

| 观察 | 值 | 含义 |
|---|---|---|
| 用户 IP 把 100 分花完 | = **50 次成功搜索** | **普通 IP 上搜索接口是通的**，站点不是全局限流 |
| 额度耗尽后的返回码 | **`11003`**（今日额度已用完） | 配额耗尽有自己的专属码 |
| 代理 IP（`status` 报 100/100） | **`13001`**，且事后额度未扣 | 与配额**无关**，是另一条路径上的拒绝 |
| 同一 IP 上换新 visitorId（fingerprint 桶满额） | 仍搜不了 | 额度 = min(ip 桶, fingerprint 桶)，**ip 桶是硬约束** |

**结论从 [推断] 升级为 [事实]**：`haisou.cc` 的搜索端点对**代理池所在的 IP 段**做了端点级拦截，
返回 13001；这与积分、匿名身份、请求头、HTTP 版本、会话都无关。普通住宅/办公 IP 不受影响。

**11003 与 13001 是两个互不相干的拒绝路径**，不要把它们当成"同一种限流的轻重两档"——
这是本次差点走错的地方。判据：11003 会伴随额度真实归零，13001 不动额度。

### 容量上限（做吞吐估算时要用）

每 IP 每天 100 分 ÷ search 2 分 = **50 次搜索/IP/天**，按 page_size=20 封顶 **1000 条/IP/天**。
即使哪天 13001 解除，单 IP 产出也就这个量级，和 sitemap 型站点（misoso 626 万条）完全不是一个量级。
**这决定了 haisou 的优先级应当排在 sitemap 型站点之后。**

### 更正：代理池不是机房 IP，是住宅宽带秒拨池（2026-09-03 晚，RDAP 实测）

此前多处记着「蜻蜓＝机房 IP，可能整段被标记」，**这是错的**。对池子里的 IP 做 RDAP 查询：

| IP | 注册网段 | 归属 |
|---|---|---|
| 119.101.54.192 | 119.96.0.0/13 | CHINANET-HB 湖北电信 |
| 218.86.67.52 | 218.85.0.0/15 | CHINANET-FJ 福建电信 |
| 140.250.147.83 | 140.250.0.0/16 | CHINANET-SD 山东电信 |
| 49.87.0.119 | 49.64.0.0/11 | CHINANET-JS 江苏电信 |
| 27.152.127.141 | 27.152.0.0/17 | Quanzhou Broadband MAN 泉州宽带城域网 |

全是**电信省级宽带/城域网**，也就是家宽 PPPoE 拨号池（"秒拨"），不是 IDC 机房段。

**这条更正会改变结论的走向**：

- 通用的「代理/VPN/机房检测」类数据库对这些 IP 大概率判**低风险、住宅**——
  因为按 ASN 和网段性质它们确实就是住宅。指望这类库预筛出"哪个 IP 会被 haisou 拒"是不现实的。
- 只有专门追踪**住宅代理网络**的厂商（Spur.us 一类）才有可能识别，且都是商业付费。
- 站点更可能是**按行为**把这些秒拨段拉黑的（这些池子被爬虫反复复用），
  这种黑名单没有公开数据库能镜像。

**最便宜也最准的判据其实是站点自己**：13001 不消耗积分，所以对每个新 IP 发一次搜索探路是**零成本**的，
结果比任何第三方分数都准。要做 IP 预筛就用观测结果建黑名单（redis 记 IP → 拒绝时间），
不要引入第三方纯净度库。

**可迁移教训**：判断代理是不是"机房 IP"要查 RDAP 的网段归属，不要凭代理商的品类名脑补。
判错了会把排查方向整个带偏（"换住宅代理"这个建议其实是原地打转，因为用的就已经是住宅 IP）。

### 常态化探路（2026-09-03 晚已上线）

`osec-spider-go/scripts/haisou_watch.py` + 本机 crontab，每天 09:30 跑一次，结果邮件通知。

    30 9 * * * \
      /home/peterq/dev/env/miniforge3/bin/python3 scripts/haisou_watch.py --proxies 3 \
      >> /tmp/haisou_watch.log 2>&1

判定口径（**`unknown` 与 `blocked` 必须分开**，这是设计上最关键的一点）：

| 结论 | 条件 | 含义 |
|---|---|---|
| `released` ✅ | 任一代理搜索成功 | 站点放行，要立刻补联网验收 |
| `blocked` ⛔ | 全部 13001 | 维持现状 |
| `quota` ⚠️ | 命中 11003 | 不该出现，说明账本或探路逻辑有问题 |
| `unknown` ❓ | 没代理 / 全网络错误 | **我们这边坏了**，不是站点的结论 |

把 `unknown` 混进 `blocked` 会让「探路早就没在跑了」这件事被无声吞掉——
同步进程一停、白名单一过期就会这样，而那恰恰是最容易发生又最难察觉的失效。

邮件通道：`POST http://cf-worker.peterq.cn/notify_admin`，
body `{"subject","htmlContent","source"}`，实测返回 `email_send_ok`。
这是本项目通用的管理员通知入口，其他 cron 任务也可复用。

⚠️ 探路依赖本机常驻的 `redis-topic-sync` 与 `dev_add_local_ip_to_qingting`，
两者**不会开机自启**，重启后探路会一直报 `unknown`。
默认每次都发邮件；嫌吵可以加 `--only-on-change`（代价是失去心跳，死掉和无变化看起来一样）。
