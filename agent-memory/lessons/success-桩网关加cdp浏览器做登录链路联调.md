# 成功经验：桩网关 + CDP 浏览器做登录链路联调

## 问题

后台登录改造（GitHub OAuth）涉及"浏览器打开登录门 → 跳转 GitHub 授权 → 回调换票 →
RTC 握手重连 → 渲染正文"这条完整的用户可见链路。这类改造的两轮静态审查（含专门的验收
Agent）都判定通过，但真实浏览器一测就发现登录门根本不出现（见
`lessons/failure-握手回包附加字段被传输层丢弃.md`）。

## 适用条件

改造涉及浏览器端可见的交互流程（登录、弹窗、跳转、状态展示），且这条流程依赖
"前端状态 ← 后端错误/事件 ← 某种传输层"的多跳链路——静态审查只能分别验证每一跳
本身的代码正确性，验证不了数据能否真的跨层传递。

## 推荐做法

1. **造一个只保留被测链路的桩服务**：不依赖 redis/mysql/ES 等重依赖，只实现真实的
   `rtcHandshake` + 最小可用的业务 RPC（够撑起页面骨架即可）。本次用
   `osec-spider-go/tools/stubgw`。
2. **用带登录态的调试浏览器实测**：`MEMERY/scripts/agent-browser.sh` 启动一个独立
   profile 的 Chrome（人工登录一次 GitHub 后长期复用登录态），`MEMERY/scripts/cdp.py`
   通过 CDP 导航、求值、填表、截图，驱动整条链路走一遍。
3. 桩网关 + 调试浏览器都由主控（有权限做这类验证的一方）持有，子 Agent 只管改代码，
   改完汇报，由主控在真实浏览器里复测——保持"谁改代码谁不自证"的验收独立性。

## 原因

- 桩服务去掉了 redis/mysql/ES 依赖，启动快、状态可控，能反复快速复现同一个握手场景
  （成功/403/换票失败/非组织成员等），比连生产或搭一整套依赖轻量得多。
- 真实浏览器 + CDP 能看到"用户真正看到了什么"，这是静态审查和单测都无法覆盖的最后一环——
  本次两个阻断级问题都是"两端代码分别看都对，合起来不对"，只有端到端真实运行能暴露。

## 示例

本次靠这套方法论抓到两个"代码看起来完全正确"的阻断级问题：
1. 握手 403 回包的业务字段被 RTC 传输层的统一取消路径丢弃（登录门不出现）；
2. 登录失败的具体原因被下一次无 code 的重试用通用"未登录"覆盖掉。

两个问题的表现都是"逻辑链条上每一环单独看都通过审查，串起来才会露馅"，
不亲自在浏览器里点一遍看不出来。

## 注意事项

- 桩服务要**明确写清楚它只覆盖了哪条链路**，不能拿桩服务的通过当作全链路（含真实依赖）
  的验收结论；上线前仍需在真实/预发环境按标准流程验证。
- 调试浏览器的 profile 目录含 cookie 等登录态，严禁提交/外泄，见
  `procedures/workflow-带登录态的浏览器自动化.md`。

## 可迁移范围

任何"改造涉及浏览器可见交互 + 多跳传输链路"的任务都适用，尤其是本仓库自研的
RTC-gRPC 传输（历史上没有走过标准 HTTP mock 工具链，桩服务是目前性价比最高的验证手段）。
纯后端逻辑改造、或前端改造不涉及跨层状态传递时，静态审查 + 单测已经足够，不必上桩服务。
