# 站点爬虫运行时重构方案对比

## 1. 现状事实（2026-09-18）

- `deploy.sh` 共 36 个服务映射；站点遍历型 `bbs_*` 11 个、关键词型 `keyword_*` 6 个、网盘加载 5 个、下载/网页链路 7 个、网关与运维若干。[事实]
- 约定「一站 = 一子命令 = 一 docker 容器」，同一 62 MB 单二进制；5 台 2 核 1~3 GB 主机，**混跑大量非本项目容器**，spider 不是唯一租户。[事实]
- 每站 500~650 行 Go + 300~470 行单测；调度/去重/限速/提交/保活已由 `services/spider-common/sitecrawler` 骨架承担（09-16 刚落地）。[事实]
- 站点全部是纯 HTTP（JSON 接口 / SSR HTML / sitemap / id 枚举），无浏览器渲染依赖。[事实]
- 爬虫一律走代理池；蜻蜓代理按**客户端 IP 白名单**授权，`proxy` 进程负责同步白名单，代理列表经 redis 发布给各爬虫。[事实]
- 进程大多数时间在按 `MinRequestInterval` sleep，CPU 几乎空闲；成本主要是内存与容器数带来的机器占用。[推断]
- 已有 FC 经验：`resource_download_fc`（Go runtime，北京）、`nc-app-prod-cdp3`（custom-container，杭州）；已知坑：WS 断开即冻结、超时切断。[事实]

## 2. 对 FC + Lua/WASM 方案的可行性判断

技术上可行，但收益与"进程多"这个问题不直接对应，且有三个硬卡点：

1. **代理白名单**：FC 出口 IP 动态，进不了蜻蜓白名单；必须 VPC + NAT 网关 + 固定 EIP（实例费+EIP+流量，估 ¥150~300/月 [待确认]），或与供应商确认支持账号密码鉴权。这一项可能吃掉全部节省。
2. **计费模型**：FC 按实例活跃时长计费。爬虫的限速 sleep 若留在函数内，等于付钱等待；必须把节拍搬到网关调度（timer 触发 → 派发页级任务 → 函数只做取+解析，单次 <1 s）。这是架构改造，不是换语言。2024-08 起按 CU 计费；**单小时有调用的函数最低 0.01 元/小时**（≈ ¥7.2/月/函数），11 站各一函数最低就 ≈ ¥80/月，接近一台 ECS；用「一个通用运行时函数 + 脚本」才能压到一份最低费。
3. **Lua/WASM 的价值点是"站点逻辑变成数据、可热更、同一运行时"**，不是省钱。代价：11 站 ~6k 行 Go + 4k 行测试重写；Lua 需自建 http/gjson/goquery/regexp/gzip/redis 绑定（2~3 周）；WASM（wazero）WASI 无 socket，同样要宿主导出 http，多语言与沙箱是我们不需要的收益。团队 Go 栈，脚本层弱化类型与测试。

结论：Lua/WASM 与 FC 是两个独立决策；单纯为了压进程数，两者都不是最短路径。

## 3. 四套方案对比

| 维度 | A FC + Lua/WASM 通用函数 | B 单进程多站点宿主（Go，ECS） | C Go 站点直接上 FC（timer/队列驱动） | D 宿主进程内嵌 Lua 脚本引擎（ECS） |
|---|---|---|---|---|
| 改造量 | 6~8 周（运行时+绑定+11 站重写+基础设施） | **3~5 天**（`bbs` 宿主命令、每站 goroutine+panic 恢复、deploy.sh 映射） | 2~3 周（Site 复用，调度改 timer/页任务，NAT） | 3~4 周（运行时）+ 每站 1~2 天迁移 |
| 进程/容器数 | 0 常驻（函数） | 11 → 1~2 | 0 常驻 + 网关调度 | 1~2 |
| 新增月成本 | 计算 ≈ 几元；NAT 固定 IP ¥150~300 [待确认] | 0 | 同 A | 0 |
| 隔离性 | 强（实例级） | 弱（同进程；大站单独分组可缓解） | 强 | 中（脚本沙箱） |
| 热更新 | 脚本从 OSS 拉取，秒级 | 重新部署（releases/rollback 已有） | 重新 s deploy | 脚本热加载 |
| 调试/测试 | 弱，需重建测试体系 | 现有单测全部保留 | 单测保留，线上调试靠 SLS | 中 |
| 与既有决策 | 新增基础设施 | 符合"不增新进程"倾向 | 需新增网关调度职责 | 符合 |
| 主要风险 | 白名单/成本倒挂；重写引入回归 | 一站 OOM/死循环拖累同组 | 全量长轮次超时；限速搬家复杂 | 绑定层长期维护 |

## 4. 推荐路径

1. **先做 B**：`bbs` 宿主命令按配置装载 N 个 Site，每站独立 goroutine + panic 恢复 + 退避重启，日志前缀用 `Name()`；misoso 这类大站单独一组。立刻减 ~10 个容器，零新增成本，单测与 redis 键全部不变。
2. **验证真实收益**：B 上线后看是否能实际退掉某台主机（混租情况下不一定）；退不掉则"进程多"只是观感问题，成本压力另找原因。
3. **站点数 >30 或需要非开发人员改站点时再评估 D**（脚本化），在 B 的宿主上加 Lua 引擎，逐站迁移。
4. **FC（A/C）只在两个前提同时满足时启动**：代理供应商支持非 IP 白名单鉴权（或 NAT 费用可接受）；且工作负载能改成事件驱动（增量轮次短、全量派页任务）。
