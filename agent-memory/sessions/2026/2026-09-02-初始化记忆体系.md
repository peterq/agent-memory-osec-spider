# 2026-09-02 会话记录

## 完成事项

- 通读 COMMON / SPIDER / STORAGE / API 四个仓库的目录结构、入口、proto 契约、配置与部署脚本
- 实测四个仓库的 `go build ./...` 状态
- 创建 `agent-memory/` 目录及 12 个记忆文件（总览、索引、偏好、背景、5 篇知识、2 篇流程、3 篇 current）

## 关键发现

1. `PPIO → 1s` 重命名只做了源码 import，`go.mod` 的 module 行与 replace 路径没跟上，
   导致 COMMON / API / STORAGE 三个仓库本地编译全部失败。SPIDER 在提交 `774e7bc init agent` 中已修好自己的 replace。
2. 磁盘目录名与 Go module 名系统性不一致（`osec-spider-go` ↔ `enfi-spider-go`，
   `osec-resource-api` ↔ `enfi-resource-api`），检索时两个名字都要试。
3. SPIDER 有 2 个包存在与本次改动无关的存量编译错误。
4. 配置文件里有大量明文密钥，已在 `current/risks.md` 和部署流程文档中标注为禁止外泄。
5. 系统的核心抽象是"gRPC 包装的 Redis 队列"：三段式 Pop/Keepalive/Done + seq 校验 + 永久失败标记。

## 遇到的问题

  → 已沉淀为约定：跨仓库操作一律用绝对路径或 `go build -C` / `git -C`。

## 值得沉淀的经验

- 判断多仓库项目"能不能编译"必须逐仓库实测，不能从 import 路径推断，
  尤其在组织重命名进行中的项目里。
- Go 的目录型 `replace` 对被替换模块 `go.mod` 的 module 名不做严格校验：
  SPIDER 能正常编译 COMMON 的包，而 COMMON 自己 `go build` 却失败。
  所以"下游能编译"**不能**证明上游模块声明是对的。
