# 会话摘要：res_lc_* 数据纳入管理后台

## 完成事项

后台 lifecycle 模块此前只能按 url/id **精确查单条**资源，64 张分表与 `res_lc_event`
没有任何列表化入口。本次补齐 4 个**纯只读**能力（用户明确"全都要 + 只读 + 并行 agent 开发"）：

| 能力 | rpc | 前端页面 |
|---|---|---|
| 分表资源列表（多条件筛选 + 分页） | `ListResources` | 资源列表 |
| 分表统计看板（行数与维度分布） | `TableStats` | 分表统计 |
| 事件流水查询 | `ListEvents` | 事件流水 |
| 67 表体检 + DB↔ES 对拍 | `TableDiagnostics` | 表诊断 |

提交（均已 push）：

- COMMON `3c0f4f8` 契约、`35eb8fd` 注释口径修正
- SPIDER `0b35940`（合并 `3ab8237`，1500 行纯新增，未改任何现有文件）
- NC-JS `8aed2fd`（合并 `d7f0d23` + 两个验收修复 `72489b5` / `2149b13`）

**只开发未部署**——网关双机在跑 `hotfix/p4-bootstrap`，P4 全量 bootstrap 完成前不能动。

## 关键发现

1. **[事实] 8 个 proto 的 `go_package` 仍是重命名前的 `github.com/PPIO/...`**：
   重跑 `rpc/spider/gen.sh` 会把失效 import 写回生成代码（`go build` 直接报
   "no required module provides package"）。已统一改为 `github.com/1s/...`。
   前端 `protc_gen.sh` 也缺 `node_modules/.bin` 的 PATH（protoc-gen-ts 找不到），已补。
2. **[事实] proto3 零值与 `-1` 哨兵冲突**会静默查错数据，详见
   `lessons/failure-proto3零值与负一哨兵冲突.md`。
3. **[事实] `dueOnly` 三处口径其实一致**（`status=1 AND next_check_at<=now`，与 `ScanDue`
   走 `idx_due` 的口径、`withDueBacklog` 相同），只是 proto 注释漏写 `status=1`。
   但由此暴露：`status` 与 `dueOnly` 是独立条件，同时选「失效」+「只看到期」会拼出
   `status=2 AND … AND status=1 AND …`，**恒空且不报错**。前端已加防呆（锁定状态为「有效」）。
4. **[事实] `pnpm -F <pkg> test:unit -- --run` 会被 pnpm 拼成 `vitest "--" "--run"`**
   而进入 watch 模式，产生一次假失败；用 `CI=true` 环境变量规避。

## 做出的决策

- **第 4 项「分表运维」在只读约束下做成纯诊断**：报告缺表/缺列/缺索引/对拍差值，
  把建议命令（`lifecycle_init_tables`）列进 `suggestions` 交人工执行，后台不执行任何 DDL。
- **DB↔ES 对拍改用 `Service.Stats()` 的 ≤60 秒缓存快照**（后端实现方提出，主控采纳）：
  原方案逐索引调 `CountByIndexName` 是一次全量 64 表 `COUNT`，在 bootstrap 高写入压力下
  等于每次诊断都制造一次全表扫描。换成缓存快照后代价归零，精度从"这一刻"降为"≤60 秒前"，
  口径写进响应 `note` 并在前端展示。
- **子 Agent 任务描述改为文件式简报**（用户要求），见下。

## 遇到的问题

- 前端子 Agent 中途**自行转派了一个子代理然后停在"等待回报"**，工作留在工作区未提交。
  唤醒它并明确要求"自己核实、不要再转派"后才收尾。它核实时发现转派出去的那份
  **N2 根本没落实**，是它自己补的。
- 验收方指出流程疏漏：主控在 NC-JS 生成了 TS 契约却**没有当场提交**，前端面对工作区里
  来路不明的改动，只好自己重新生成一遍。结果正确但属于重复劳动。

## 值得沉淀的经验

1. **契约类产物主控生成后要当场提交**，否则子 Agent 面对工作区里的陌生改动会困惑或重做。
   已补进 `procedures/workflow-子agent任务简报.md` 的注意事项。
2. **跨端契约陷阱靠单侧测试测不出来**（两侧各自都"符合契约"），要靠实现方主动上报 +
   主控在两端之间做一次对齐。本次 N1/N3 都是这么发现的。
3. **不要采信子 Agent 的转述**。前端核实 N2 时发现下游根本没做；验收方复核时又发现
   前端漏了 `diff=-1`（未知态）会被误标成"有真实差异"，且 mock 数据把这个场景写错了，
   导致它此前从未被真正测过。**每一层都独立复核，每一层都抓到了上一层的漏网之鱼。**
4. 验收方用恶意 `orderBy: "id; DROP TABLE res_lc_quark_00; --"` 实测白名单拦截，
   比只读代码更有说服力——验收判据里写"构造一个恶意输入验证"是值得保留的写法。
