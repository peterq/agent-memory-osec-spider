## 流程与分工（实测有效）
Phase 0（Sonnet 抽取 + 主会话审 proto + Sonnet 生成代码）→ Wave 1 五 Agent 并行（网关/STORAGE 用 Opus，checker/API/前端用 Sonnet；SPIDER 两个 worktree，其余仓库分支）→ Sonnet 合并（仅 config.go 一处冲突）→ Opus 端到端验收（本地 docker ES 6.7/MySQL/redis，真实进程链路，269 次工具调用，抓出 2 阻塞 + 3 重要缺陷并直接修）→ Sonnet 修前置项 → push。

## 关键发现
- 见 `lessons/success-生命周期改造验收发现.md`（refresh=true、BatchUpsert !id、作业 recover、幂等在轮换后再验、别名判据）。
- v2 `/api/v2/search` 缺省 `v=1` 走 `SearchV1`，v3 必须镜像 `v` 分派，否则灰度对拍必然不一致。
- STORAGE `deploy.sh` 只部 res2，但 res1 也跑着 storage gateway → 上线要手动覆盖 res1。
- 配置分发：网关 gw_config 走 OSS；`services.lifecycle` 在宿主机 config.yaml（不分发）→ `enabled` 靠 redis 热更新参数打开；STORAGE/API 配置是宿主机本地文件，需 ssh 追加。
- osec-res1 根分区 82%（21GB 的 `keyword_upyunso.out` 在长）。

## 遇到的问题
- **部署子 Agent 两次被 auto 权限分类器拦截**（完整 P0~P2 版本与仅 P0 版本都被拒），无法由主会话发起生产部署；已停下等用户决定。
- 一个 Sonnet 修复 Agent 把任务再转派给自己的子 Agent 后先行返回（"等通知"模式），最终子 Agent 都完成了，但要靠检查 git 工作区判断是否仍在进行。
