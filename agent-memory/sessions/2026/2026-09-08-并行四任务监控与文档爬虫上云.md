## 关键发现

### 主控 hub 审查抓到的阻塞级缺陷（`246751e`）

`spider.go` 在命令分发前无条件 `db.Redis(config.Config.Services.Proxy.Redis)` 初始化代理监控。
`db.Redis` 对"redises 里没有这个名字"是 **log.Fatal**、对"连不上"是 **panic**；
而 2026-09-08 配置按服务拆分后，**网关那份配置根本没有 `services.proxy` 节** ——
照原样上线，网关一启动就 Fatal。同一个包的读取侧 `proxy_admin/redis_resolve.go`
把这道防线写得很完整（注释里都写明了 log.Fatal 的危险），写入侧却漏了。
→ 沉淀为 `lessons/failure-旁路能力初始化拖垮主流程.md`

同批修的还有：`Do()` 的三个"没拿到响应就返回"分支完全不上报，使代理池枯竭/全员超时
这类最该被看见的故障在成功率里既不进分母也不进分子；`classify()` 在 `res==nil` 时
仍调业务分类器，而业务分类器普遍直接读 `res.StatusCode/res.Body`。

### 验收 Agent 的有效发现

- A：`effectiveRule` 的"preCheck 走更大 backlog 缺省阈值"语义**没有单测**（已补 `3482e98`，
  三个用例，其中一个专门盯 proto3 optional 的"未设置 vs 覆盖成 0/负数"）；
  `logs.go` 的 `AuditLogs` 注释残留旧 service 名。
- B：`quark_checker.isRateLimited()` 把"200 + 空 body"判为限流，但 `valid_quark` 代理池
  没配 `ClassifyResult`，默认分类器只认 429/403 → 该场景"被站点封禁"被系统性低估
  （已修 `d6a4d54`）。B 还**独立复跑**了 FC Chrome 的本地 CDP 注入验证与 doc-crawler 端到端桩测试，
  没有采信开发 Agent 留下的日志文件。

### 顺带修掉的存量问题

- `rpc/spider/gen.sh` 从来没有包含 `queue_admin.proto`（改协议要手工敲 protoc）。
- `queue_admin/logs.go` 的 `auditLogServiceName` 是 `spider-queue_admin`，但 queue_admin
  已于 2026-09-04 并入网关进程，实际 service 是 `spider-gateway` ——
  **`AuditLogs` 在线上从来查不到任何审计记录**。
- bnd 两个消费者零日志、`CommitResLink` 重复提交分支静默、入库结果只走 stdout 不进 SLS。

## 做出的决策

- 失败率统计从"每次现查 SLS"改成 **redis 分钟桶**（由已有的 60s 指标轮询顺带写入，零额外 SLS 开销）。
  理由：SLS `search` 的 limit 被硬夹到 200，窗口拉到 1 小时后一定扫不全，结果会系统性偏低。
- 代理池监控：`proxy-client` 只加 hook（`RegisterHook`/`Scene`/可选 `ClassifyResult`），
  上报逻辑全在独立包 `illuminate/proxy-monitor`，消费端每个池只加一行 `Scene:`。
- 链接追踪：全链路无 trace id，用**分享 id 全文检索**跨阶段串联，同时各阶段补 `link_key`
  顶层字段，等 SLS 建索引后可切精确查询（开关 `services.queue_admin.sls.link_key_indexed`）。
- 文档爬虫上云：**云端油猴脚本不连 gRPC/WebRTC**，只解析 + `console.log` 约定协议回传，
  链接提交与任务上报统一由 doc-crawler 走标准 gRPC。移植面和失败面都大幅收敛。

## 遇到的问题

- 无生产凭据 → SLS 查询、FC 部署、Tampermonkey 安装路径都无法联网验证，全部如实标注。
- Tampermonkey 没有扩展包实物，"从 URL 导入"的 DOM 选择器只能靠推测；
  因此 doc-crawler 缺省走**已本地验证过**的 CDP 主世界注入通道。

## 值得沉淀的经验

- **旁路能力（监控/埋点）的初始化必须能降级**，不能用会 Fatal/panic 的基础设施函数
  ——同一个包里读取侧防住了、写入侧漏了，说明"知道危险"不等于"每处都防住"，
  hub 代码必须由主控逐行看。
- **埋点只覆盖"拿到响应"的分支，等于让最严重的故障隐形**。设计观测点时要先问
  "失败得最彻底的那条路径会不会被记录"。
- Phase 0 把共享文件（proto、菜单、mock、契约接线）一次做完，5 个 Agent 并行改 5 个仓库
  **零冲突**；NC-JS 无法用 worktree（pnpm workspace），改用"文件边界互斥 + 禁止子 Agent commit"
  同样有效。
