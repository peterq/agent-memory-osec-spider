## 关键发现

1. **osec-resdb 的 `es_endpoint` 指向已下线的旧 ES 集群**（`es-cn-nwy39…`，DNS 已无记录），
   lifecycle 的 fail-fast 把这个长期存在的哑故障暴露出来。该机 `worker.log` 已 3.7 GB，
   一直在刷解析失败 + nil 指针 panic，**save-worker 的 ES 写入路径早就坏了**。
   详见 `lessons/failure-resdb的ES端点指向已下线集群.md`。
2. **新索引写入量一度高于旧索引**，不是双写漏写：`saveLegacy` / `upsertResourceLegacy` 会先按
   version 去**旧索引**查重并跳过，而新链路查的是几乎为空的新索引，去重命中率为 0，故 ramp-up 期
   新索引 index op 更多，bootstrap 之后会收敛。
3. **新旧索引 `_source` 在双写期存在字段差异**：`upsertResourceLegacy` 从**旧**索引继承
   `client/refer/createtime/meta`，而 `lifecycle.BuildParentDoc` 的 `inheritFields` 从**新**索引继承——
   P3 期间首次写入新索引的资源没有历史值可继承。**P4 bootstrap 对这批 id 是覆盖还是跳过必须先确认**，
   否则会永久缺 `client/refer/likes/views/downloads`。
4. **API 线上流量全部落在 osec-res2**：osec-res1 的 `res-api` 近 60 分钟只有 1 次请求。P5 灰度要按此设计。
5. **现网没有 `resource_valid` 索引**（HTTP 404），`checkValid` / `queryValidAndPwd` 在 **v2 和 v3 上同样**失效，
   与本次上线无关，属既有故障。
6. 短窗口测 ES `index_total` 速率会被爬虫流量抖动误导（2.8 → 28.5 ops/s 都出现过），
   至少要 10 分钟窗口才有意义。

## 做出的决策

- **不改 osec-resdb 的 `es_endpoint`**：属于改动既有配置内容，超出本次授权，留给用户拍板。
- resdb 的新二进制与新配置留在 `storage.lc` / `config.yaml.lc`，端点修好后可直接换回，不用重新传。

## 遇到的问题

- resdb worker fail-fast → `--restart always` 导致重启循环，46 秒内完成回滚（rm -f → `mv storage.old storage`
  → `cat config.yaml.bak.20260906 > config.yaml` → 重跑 dockerRun），恢复后 0 fatal。

## 后续行动

- 用户决策 osec-resdb 的 ES 端点是否修复；修好后补 worker 侧双写。
- P4 启动前确认 bootstrap 对 P3 期间已写入 id 的覆盖策略（见关键发现 3）。
- `resource_valid` 索引缺失单独立项。

## 值得沉淀的经验

- **改宿主机配置前先 `cp -n` 备份**，用 `awk` 生成新文件后 `cat > 原文件` 回写（保留 inode 与属主），
  再 `diff 备份 新文件` 确认"只多新增行"。宿主机没 python3 时把文件 `scp` 回本地校验，用完即删。
- **上生产前先在本地用一份合成 config 跑一遍 `Resolve()`**，确认键名/缩进能被代码真正解析，
  避免到生产才因拼错键触发 fail-fast。
- **部署有 fail-fast 的服务前，逐台验证配置里的外部依赖**（DNS + HTTP），不要假设同一集群的机器配置一致。
- 需要查网关 DB 时优先用 `LifecycleRpc.QueryResource` / `Overview`，**不需要 MySQL 凭据**，
  且能同时拿到 DB 元数据、ES 命中位置、`foundInLegacy` 与事件流。
