# 会话摘要

## 完成事项
1. 主会话亲自调研：经 osec-res1 跳板实测生产 ES（集群/索引/mapping/segments/父子文档统计/按月分布/join 字段能力）
   与 MySQL（表清单/容量），通读写入/读取/清理链路代码。结论沉淀到 `knowledge/architecture-es索引现状.md`。
2. 主会话写方案要点（design-brief：需求原文、实测事实、决策 D1~D9、待确认 Q1~Q5）→ **Opus** 子 Agent 撰写
   PRD v1.0（2462 行）→ 主会话复核 → **Sonnet** 子 Agent 修订 + 5 仓库路径/JSON/proto(protoc 编译)/DDL 核验 → **v1.1（2705 行）**。
   产物：`osec-spider-go/PRD/res-lifecycle/README.md`。
3. 沉淀脚本 `osec-spider-go/scripts/es_survey.sh`（ES 体检：健康/索引/磁盘/父子统计/无 join 统计，实跑通过）。
4. 进度邮件 3 封（notify-admin.sh）。

## 关键发现
- **旧索引里有 2966 万无 join 字段的父文档**（百度 2905 万，文件清单在 nested filelist，nested 内部文档 3.08 亿），
  第一次只按 `join=resource` 统计得到 1530 万，**漏掉了三分之二的资源**。百度资源至今仍走 STORAGE
  `UpsertResource` 小资源路径写入且不带 join。真实资源总量 ≈ 4440 万。
- ES 6.7 上 `terms join#resource` 与 `term join=resource` 均实测可用（批量搬迁子文档与父文档过滤的基础）。
- Opus 撰写 Agent 自己发现了"小资源路径父文档无 join"的隐患（代码层面），与主会话的 ES 实测互相印证。

## 做出的决策
- 见 `decisions/decision-2026-09-04-资源索引生命周期改造方案.md`（D1~D9 + 三条异议裁定 + 无 join 更正）。

## 遇到的问题
- 本机不能直连 ES，`ssh osec-res1` 上 curl；res1 无 python3，JSON 要拉回本地解析。
- MySQL DSN 口令含 `@`，按第一个 `@` 切分会拿到错口令（Access denied），要按 `@tcp(` 切。
- `_stats` 接口经 ssh 管道拉取时报 `Failed writing body`，本次未取到读写 QPS 基线，列入 PRD §15.3。

## 后续行动
- 用户确认 PRD §14.2 的 Q1~Q6 后进入 Phase 0（契约/DDL/template 由主会话定），再按 §13 派 sonnet 并行开发。
- 上线前基线采集：读写 QPS、bnd checker 探测吞吐、无 join 文档 `_source` 大小抽样。

## 值得沉淀的经验
- **统计 join 索引一定要同时查 `must_not exists join`**：同一索引可能混着两代文档形态。
- Opus 写方案 + Sonnet 核验的分工再次有效：Sonnet 核出 mapping 缺字段、JSON 非法、行号偏差 4 类问题；
  Sonnet 又自行派出 5 个仓库核验子 Agent 并行，效率高。
- 撰写 Agent 的"异议"要由主会话逐条裁定并写回文档，不能让正文与异议长期并存。
