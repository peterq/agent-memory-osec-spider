**验证**：四个仓库 `go build ./...` 全部 exit 0；改动的两个包 `gofmt` 干净。

## 关键发现

1. **改 go.mod 只改 replace 不一定够**：STORAGE 改完直接 build 报
   `go: updates to go.mod needed; to update it: go mod tidy`，必须跑 tidy。
2. **tidy 有副作用**：STORAGE 的 `go` 指令被提到 1.23，并顺带升级了 aws-sdk-go、logrus、
   mysql driver、easyjson，`go.sum` 裁掉 2880 行。原因是它现在真正依赖本地 SPIDER 模块，
   要满足 SPIDER 的最小版本要求。→ 已记入 `current/risks.md` R6 / `tasks.md` P1。
3. **API 之前只是"看起来"配了 spider 依赖**：`replace PPIO/pan-client-core` 那条是死配置，
   实际链路上用的是 `github.com/1second/pan-client-core`。
4. `gw_contract.GwQueue[T].PushTask` 收的是**值**类型 `PushTaskParam[T]`，不是裸 payload 指针；
   参考实现在 `services/gateway/download_scheduler/web_res/head_url.go:153`。

## 做出的决策

- **修而非删**：`devops_res_reindex` 虽是未挂进命令表的半成品，仍按原意补全而不是删除
  （用户指令是 "fix: 编译错误"）。其 `root = "/"` 的可疑取值不擅自改动，作为待确认问题记录。
- **replace 一律用相对路径**：便于其他机器上 clone 后直接可用。
- **不动 `resource.SaveBaiduResource` 的按值签名**：`go vet` 告警是全局性的既有问题，
  超出本次范围，改动会波及多个调用点。

## 遇到的问题

- `go mod edit -fmt` 会重排 require 块：`github.com/1s/...` 排在 `github.com/1second/...` **之前**
  （`/` 的字节序小于 `e`），手工插入时容易排错，直接跑 `go mod edit -fmt` 即可。

## 值得沉淀的经验

- 多仓库重命名的正确顺序：**先改被依赖方（COMMON），再改依赖方**，每改一个仓库立刻 build 验证，
  不要四个一起改——否则报错信息会互相掩盖。
- 修"类型不匹配"类编译错误时，先找同包内是否已有类型别名（本例 `bnd_resolver.go` 顶部的
  `QueueTransfer2Tmp` 等），用别名而不是重新拼泛型实参，能避免再次写错。
- 修半成品代码时，找**同一 API 的现有正确调用点**当模板
  （`head_url.go` 的 `PushTaskParam`、`search_export.go:297` 的 `InitProdEs`），比自己推断可靠。
