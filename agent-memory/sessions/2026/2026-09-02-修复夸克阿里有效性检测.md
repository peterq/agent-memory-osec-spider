# 会话摘要：修复夸克/阿里云盘链接有效性检测

## 完成事项

用户给了 15 条阿里 + 15 条夸克样本链接，反馈检测"出问题"，怀疑网页结构变了。

先写联网用例复现，再定位、修复、复测：修复前 quark 4/15 报错、ali 6/15 报错；
修复后两个仓库都是 **0/15 报错，且两套实现对 30 条链接的结论完全一致**。

## 关键发现

不是网页结构变了，接口和字段都没动，是**判定逻辑覆盖不全**，三类问题：

1. **夸克 `code=41004 文件不存在` 从未被识别** → 落到 `unknown status` 返回 error（4/15）。
   原实现只匹配中文文案，漏了这一种。
2. **阿里 `TooManyRequests`（HTTP 429）被当成未知错误**（5/15）。
   API 侧的 `aliValid` 没有任何 429 处理，直连抽样就能稳定复现；
   SPIDER 侧的 `request()` 早就有 429 重试，两边不一致。
3. **阿里 `ShareLink.ContentInvalid` 不在 API 的失效码表里**（1/15）。
   SPIDER 的码表是全的（含 `ContentInvalid`、`NotFound.Drive`），API 的少两条。

额外发现一个反向误判：`boe7q6JL1mx`、`4Vn3DqGPCQ5` 两条阿里链接
`share_title` 正常、`file_count=1`，但 `file_infos` 是空数组——内容已被删除/屏蔽，
链接实际是死的，API 侧却报有效。SPIDER 侧因为多查一次 `file/list` 反而判对了。

## 新增或改变的事实

- 夸克失效业务码表、阿里失效码表、限流表现形式，均已实测登记到
  `knowledge/domain-网盘有效性检测.md`。
- 阿里 `bj29` 域的 `need_check_pwd` 恒为 true 不携带信息，真正的密码标志是 `has_pwd`
  （无密码时该字段不返回）。`alipan_checker.go` 那段看着可疑的代码结论其实是对的，别改。

## 做出的决策

- **判定改为业务码优先、文案正则兜底**，并把判定函数改成返回 `(valid, known)`，
  `known == false` 时向上报 error 而不是返回"失效"。
  理由：判失效会触发 ES 删除（API）和 `DeleteResourceTask`（SPIDER），不可逆，
  宁可对外返回 -1 也不能误删。
- **API 侧补上"内容已空"的判定**：`file_count > 0 && len(file_infos) == 0` 判失效。
  选择复用同一次请求的 `file_infos` 字段，而不是照搬 SPIDER 的三请求流程，
  避免对外接口的请求量和延迟翻三倍。
- 夸克判定逻辑在两个仓库各改一份（沿用仓库现有的并行实现风格），
  没有把 SPIDER 的 `services/gateway/valid` 引入 API——不想让对外 API 依赖爬虫网关内部包。

## 遇到的问题

- 直连不挂代理跑批量样本必然撞阿里限流，一开始的探测脚本还因此超时中断。
  后来正是这个"噪音"暴露了 429 没被处理的真 bug。

## 后续行动

- 两个改动都**尚未上线**，需要部署后观察 `/v2/validShareLink` 的 -1 比例是否下降。
- 百度、迅雷的 checker 仍是纯文案匹配，有同类风险，未在本次改动范围内。

## 值得沉淀的经验

见 `lessons/success-网盘失效判定原则.md`：业务码优先、限流≠失效、未知就报错、
入口还在≠内容还在。以及排查手法——**一次跑一批样本**才抖得出冷门业务码，
单条试探会漏。
