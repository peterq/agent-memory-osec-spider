# 决策：资源 ES 索引生命周期改造方案

PRD 正文（唯一需求来源）：`osec-spider-go/PRD/res-lifecycle/README.md`。本文只记录拍板要点与理由。

## 背景
单索引 `enfi_resource_v6_250822` 1.1TB / 15.8 亿文档 / 27% 墓碑（见 `knowledge/architecture-es索引现状.md`），
搜索时检测失效即删，删除不回收空间，长期性能退化。用户要求三索引生命周期 + 关系库元数据 + 管理后台，
两套方案共存可快速切回。

## 拍板要点（D1~D9）
- D1 索引拓扑：物理索引 `res_short_YYYYMM` / `res_long_YYYY`，角色用别名 `res_lc_cur`(写, is_write_index)
  / `res_lc_prev` / `res_lc_long`，**读别名 `res_lc_all`** 一次查三索引；index template `res_short_*`(5 分片) /
  `res_long_*`(10 分片)，mapping 精简、`type` keyword、`dynamic:false`。旧索引与别名 `resource` 原样保留。
- D2 "检测" = 有效性探测（复用 `services/gateway/valid` + 代理池）；"资源有更新" 以写入链路 version 变化为准，
  不在检测里重抓文件列表。
- D3 调度器放网关 `services/gateway/lifecycle/`（与 queue_admin 同模式并入进程，leader 锁），探测 worker
  是独立进程 `lifecycle_checker`（替代 `devops_check_and_push_clear_queue`），网关不背代理池负载；长作业异步可续跑。
- D4 MySQL 分表：库 `prod-osec-spider`（gw_config.Mysql），`res_lc_<bnd|ali|quark|xunlei>_<00..15>`
  （md5(id) 前两位 hex 取模 **16**，[用户确认 2026-09-05] 由 32 改 16），64 张表 + `res_lc_cycle` + `res_lc_job` + `res_lc_event`。
- D5 节奏：新入库 7d；有效且未变 7→14→30→90；version 变化重置 7d；失效删父+子并写 `invalid_link_*`；
  有效且 90 天未更新 → long；有效且在 prev → 搬到 cur（批量 `_reindex` ids + `terms join#resource`，
  网关配置 `lifecycle.move_on_check` 默认 true，可关闭退化为轮换时整索引搬）。
- D6 轮换：月初 leader 执行 建新索引 → prev 剩余 reindex 到 cur(op_type=create) → 校验 → 一次 `_aliases`
  原子切换 → 24h 冷静期后删旧 prev；年轮换同理即"重索引"，磁盘不足退化为 `only_expunge_deletes`。
- D7 共存与切换：STORAGE 双写（新 `res_lc_cur` + 旧 `resource`，开关可关；写前存在性判定先查 `res_lc_cur` 未命中再查 `res_lc_all`）；存量 bootstrap 全量复制到新索引
  （不删旧数据）；API 新增 **v3** 接口查 `res_lc_all`（[用户确认 2026-09-05] **只做 search + validShareLink/checkValid/queryValidAndPwd**，
  detail/fileCtx 等留在 v2 → 关双写前必须先补 v3 detail/fileCtx），v2 一行不改，调用方切 v3/切回 v2 即切换/回滚。
- D8 管理后台：spiderAdmin 新分组「资源生命周期」，契约 COMMON `rpc/spider/lifecycle_rpc/lifecycle.proto`，
  走网关 7542/:8082。
- D9 实施：Phase 0 契约/DDL/mapping 主会话定；各模块 sonnet 并行、opus 验收、失败 ≤3 次重试、阶段邮件。

## PRD 撰写阶段的重要更正（2026-09-05）
- 旧索引还有 **2966 万无 join 父文档**（百度为主，文件清单在 nested filelist），真实资源总量 ≈ 4440 万而非 1530 万。
  新 mapping 的 `filelist` nested 是活字段，v3 搜索保留 nested + has_child 两条路径；bootstrap 与新写入链路统一给父文档注入 join。
  bnd 存量的检测打散窗口独立配置（建议 180 天），并新增 Q6（2013~2016 年 2150 万百度老资源是否迁入）。
- 撰写 Agent 三条异议的裁定：长索引首年 10 分片（年重索引时再评估 16）；检测时搬迁保留但加 `move_on_check` 开关；
  存在性判定先查 cur（采纳为默认实现）。

## 理由
- 别名并集让搜索改动最小；物理名带日期让轮换只是别名切换，可回滚。
- 探测与调度分离：网关是长期不重启的关键进程，代理池探测的失败率与负载不应进网关。
- version 变化作"更新"判据零额外成本，且是写入链路已有语义；重抓文件列表成本高 1~2 个数量级。
- 全量 bootstrap（而非惰性迁移）换来过渡期无重复文档、回滚无损，代价是一次 ~0.8TB 的 reindex，磁盘余量够。

## 复盘条件
- ES 升级到 7.x/8.x（join、别名语义变化）；月入库量翻倍以上（短索引分片数与轮换耗时要重估）；
- 用户对 Q1~Q5（见 PRD §14）给出不同答案。
