# 决策：阿里云盘分享根目录为空(file_count==0)判定为有效

## 背景

2026-09-16 十项提案「有效性检测合并为一套实现」(valid-unify 角色)把 SPIDER
`services/gateway/valid` 与 API `services/valid` 两套独立的阿里云盘判定合并进
COMMON `enfi-resource-common/panvalid`。合并过程中发现两边对"分享入口还在,
但根目录一个文件都没有"这种情况的结论不一致。

## 要解决的问题

`file_count == 0` 时(分享者从一开始就没传文件, 或分享是空文件夹)，要判 `Valid`
还是 `Invalid`？这个判定结果会直接影响是否删除 ES 文档，删除不可逆。

## 备选方案

1. **判 Invalid**(旧 SPIDER `dirFileCount` 的行为：`return l > 0`，根目录文件数为 0
   一律判失效)。
   - 优点：语义上"没有文件的分享等于没有价值"，能顺带清理这类空分享。
   - 缺点：没有任何业务码/结构化证据支持"这个分享失效了"——`file_count==0` 既可能是
     分享者确实清空了内容，也可能是分享者刚建好还没上传、或者文件都在根目录以外的
     位置（如果未来 API 语义变化）。用"猜"代替业务码，属于
     `lessons/success-网盘失效判定原则.md` 明确反对的模式，判失效还会触发不可逆删除。

2. **判 Valid**(旧 API 单请求实现的行为：只在 `file_count > 0 且 file_infos 为空`
   时才判失效，`file_count == 0` 落到"标题非空即有效"的默认分支)。
   - 优点：符合"没有业务码/结构化证据时不主动认定失效"的整体原则，不会因为一次
     判断失误就删掉可能仍然合法的数据。
   - 缺点：无法用"有效性检测"这条路径顺带清理掉空分享；如果确实需要清理这类空分享，
     需要另开一条独立策略。

## 最终决策

采用方案 2：`file_count == 0` 判 **Valid**。COMMON `panvalid.classifyAliShare` 保留
API 原有行为不变（`panvalid/alipan.go` 中 `Title != "" 且 !(FileCount>0 && FileInfos为空)`
即判有效）。

## 决策原因

- 有效性判定的失效结果会触发不可逆删除 ES 文档，站在"宁可多留、不误删"的原则
  （`lessons/success-网盘失效判定原则.md`）上，没有业务码/结构化字段能证实失效时，
  不应该主动把"信息不足"升级成"判定失效"。
- `file_count == 0` 不是一个失效信号——它既不是业务码，也不像
  `file_count>0 且 file_infos 为空`那样能明确推出"内容被清空/屏蔽"这个结论。
- 两套旧实现里，判 Valid 的一边（API）本来就是"更严格、有业务码支撑"的一边，
  与本次合并"以更严格、有业务码的一边为准"的整体原则一致。

## 影响

- 空文件夹分享（`file_count==0`）不会再被有效性检测自动清理，会被认定为有效并保留。
- 如果后续确实需要清理这类"内容为空"的分享，需要作为独立于 panvalid 判定契约之外的
  另一条策略（例如结合创建时间 + 持续为空的时长），不要混进 panvalid 的三态判定里。
- 影响面：SPIDER `services/gateway/valid`（`services/devops/clear_expire`、
  `services/lifecycle_checker`、`services/gateway/download_scheduler` 的调用方）与
  API `services/valid`（`/v2/validShareLink`、v3 判定）都通过 panvalid 统一走这个结论。

## 复盘条件

如果发现大量空文件夹分享长期占用资源且确认为无价值垃圾数据，可以再评估是否需要
独立的"空分享清理"策略；但清理动作应该走人工审核或更保守的多重确认，不应该复用
panvalid 这套面向"网盘接口证据"的有效性判定。
