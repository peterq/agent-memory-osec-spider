# 决策：需要全站扫描的爬虫，禁止在启动时触发全量

## 背景

`services/bbs/` 下的爬虫普遍是这个骨架（kkpans 起头，后续几站照抄）：

```go
go func() {
    for {
        p.runRound("full", p.fullSweep)   // ← 启动立刻跑一次全量
        time.Sleep(p.conf.FullSweepInterval)
    }
}()
```

即**进程一启动就跑一轮全站扫描**。

## 要解决的问题

线上服务的重启是常态（部署新版本、改配置、主机维护、容器 OOM 重拉、
`--restart always` 自动拉起）。每重启一次就重扫一次全站，代价是：

- 站点侧：短时间大量请求，容易触发限流甚至被封（本项目已有 kuakes 连接层封锁、
  haisou 接口被收紧的先例）。
- 代理池侧：代理是稀缺共享资源，全站重扫会把额度打光，拖累其他爬虫。
- 收益侧：几乎为零——增量轮本来就在覆盖新增内容，去重键也还在，
  重扫的结果绝大部分是 `skipDup`。

规模越大越离谱：misoso 626 万条、fuxipan 30.75 万条、dyyjmax 8 万条，
一轮全量以小时计。

## 最终决策（[用户确认 2026-09-03]）

- **NO**：启动时全站扫描。
- **YES**：首次全站扫描完成后，把**完成时间写进 redis**；
  后续启动先检查这个时间，**有则跳过全量**，直接进入增量节奏。

即全量的触发条件从"进程启动"改为"距上次全量完成已超过 `FullSweepInterval`"。

实现要点：

- redis 键建议 `<site>:fullsweep:lastdone`，值为完成时间戳，**不设 TTL**
  （或 TTL 远大于 `FullSweepInterval`）。
- 只有**整轮成功完成**才写这个时间；中途失败不写，下次启动仍会补跑。
- 启动时读该键：
  - 键不存在 → 说明从未完成过全量，正常跑（首次建档）。
  - 键存在且 `now - lastdone < FullSweepInterval` → **跳过本次全量**，
    按剩余时间安排下一次。
  - 键存在且已超期 → 正常跑。
- 增量轮不受此约束，照常按 `IncrementalInterval` 跑。

## 影响

截至 2026-09-03，**以下 5 个爬虫都违反该规则，需要改造**：

| 爬虫 | 文件 | 现状 |
|---|---|---|
| `bbs_kkpans` | `services/bbs/kkpan.com.go` | 启动即全量 |
| `bbs_dyyjmax` | `services/bbs/bbs.dyyjmax.org.go` | 启动即全量 |
| `bbs_fuxipan` | `services/bbs/fuxipan.com.go` | 启动即全量 |
| `bbs_misoso` | `services/bbs/misoso.cc.go` | 启动即全量（626 万，最严重） |
| `bbs_kuakes` | `services/bbs/kuakes.com.go` | 启动即全量 |

`bbs_feikuai`（`services/bbs/feikuai.tv.go`）**不违反**：它的全量是
**游标分批**推进（每轮只扫 `FullSweepBatchSize` 个 id，扫完一轮回到起点），
单轮从不做整站扫描，启动时跑的是增量轮。
这种"游标分批"结构本身就是该规则的另一种合规实现，新爬虫可优先考虑。

## 复盘条件

若将来出现"必须在启动时强制全量"的场景（如去重键被误清、站点大批量改版），
应通过**显式开关**（配置项或独立子命令）触发，而不是恢复"启动即全量"的默认行为。
