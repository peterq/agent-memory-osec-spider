# 决策：弃用 report/likes/dislikes/addViews 等文档更新类接口

## 背景
API 的 `/api/v2/report`、`/likes`、`/dislikes` 以及 `Detail` 内部的 `addViews`（`search.go:825`，受 `SwitchConfig.AddViews` 开关控制）都是对资源文档做单条 `Update`（painless script 自增计数或改字段）。

## 要解决的问题
ES 的 update 机制是"标记删除旧版本 + 写入新版本"，被删文档只在 segment merge 时才真正清理，高频 update 会让索引里堆积大量已删除文档而磁盘无法回收——这与生命周期改造要解决的"删除不回收空间、长期性能退化"是同一个根因。

## 最终决策 [用户确认 2026-09-12]
- **这类接口已弃用**：`report`/`likes`/`dislikes`/`addViews`（含 `views`/`downloads` 计数）不做 v3，不迁到 lc 索引。
- **补 v3 detail 时不得调用 `addViews`**，直接删掉该路径（不要靠配置开关关）。
- 今后 API 侧禁止新增"每次读请求顺手 update 文档"的写法；计数/互动类需求若再出现，应放关系库或 redis，而不是 ES 文档字段。
- v2 现有路由保留不动（v2 一行不改的原则），但视为死接口，不再维护。

## 影响
- `knowledge/api-v3-detail-filectx兼容性分析.md` 中"套用 LocateIndex 做 Update"的建议**作废**：`LocateIndex` 只留给 `validShareLink` 的失效删除用。
- PRD §8.1 "暂不提供的接口及影响"表里 `report/likes/dislikes/addViews` 四行的"关双写后无法更新"不再构成缺口。
- P6 关双写前置只剩 `detail`/`fileCtx`（以及是否要 `query/recommend/suggest`，待用户定）。

## 复盘条件
若产品侧重新提出点赞/举报计数需求，另立方案（关系库/redis），不得回到 ES update。

## 当前状态
生效。
