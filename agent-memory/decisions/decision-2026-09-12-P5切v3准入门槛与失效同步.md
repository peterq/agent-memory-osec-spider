# 决策：P5 切 v3 的准入门槛与 D1~D4 裁定

## 背景
09-12 P5 前置对拍未通过（首页 15 条重合度 84%）。归因两类：① 旧链路（爬虫 `url_check` + API v2 `validShareLink`）判失效只删旧索引，lc 分表仍 `status=1`，v3 首页 4% 是死链；② `match_phrase_prefix` 分片展开的排序彩票，逐 id 比较不反映用户体验；另 bnd 类 v3 慢 3~10×。

## 要解决的问题
切 v3 前到底要修什么、验什么、怎么切。

## 备选方案
- 直接按原验收口径（首页 15 条 ≥95%）调 v3 排序贴近 v2 —— 否决：v2 本身就是彩票，不是基准。
- 旧链路判失效直接 `MarkInvalid` lc 行 —— 否决：两套判定实现，误判会被放大且不可逆删 ES。
- 先切 1 个低流量入口边跑边修 —— 否决：死链是用户唯一可感知劣化，回滚虽无损但暴露没必要。

## 最终决策（[用户确认 2026-09-12]，以「执行计划」方式整体采纳）
- **D1 做且为硬前置**：网关 `clearExpire` 消费者加钩子，lc 行 `status=1 且 next_check_at>now` 时把 `next_check_at` 提前到 now，由 lc checker 自己复检；API v2 `validShareLink` 直删路径改为同时 `ReportInvalid`（与 v3 valid 同一套判定实现，可直接置失效，`Source=api-v2-search`，`EsAlreadyDeleted=false`）。
- **D2 口径改语料级**：G1 `total` 差额全部 ≤1%；G2 首页 100 条重合均值 ≥90% 且 <70% 的关键词 ≤3；G3 首页「旧索引已删」文档 = 0；G4 v2 独有 id 在 `res_lc_all` 缺失 = 0；G5 3 轮延迟 P50 ≤1.2×、P95 ≤1.1×；G6 valid 三接口行为一致。
- **D3 先 profile**：假设 `SearchV3` 对 `resType=baidu` 的 `has_child(file)` 是纯开销（百度资源无 join 子文档），证实则只在 baidu 分支去掉；不为贴近 v2 排序改打分。
- **D4 不切**：门槛全过后按 §5 灰度：`searchType=match`（~20%）先切 → 观察 3 天 → 全量 → 3 天；回滚=调用方改回 v2 路径；触发条件 v3 5xx>0.1% 或慢请求占比>v2×1.5 持续 30 min 或死链投诉。

## 影响
- SPIDER 网关重部（连带 5 个 P4 未部署提交）；API 重部。
- 上线后 24 h 关注 lc 检测队列（旧链路失效发现率全部转成 lc 复检负载）、bnd checker 代理池配额；钩子带 `legacy_hint_per_min` 限速配置以备积压。
- 存量（bootstrap 迁入但旧链路已删的行，抽样缺失率 quark 0.55% / bnd 0.05%）另行按天分批 `lc-check -trigger-check`（`TriggerCheck(force)` ≤200/批），不一次性全提前。

## 复盘条件
复测（阶段 C）任一门槛不过只回到对应阶段；灰度期触发回滚条件即回滚并复盘。

阶段 A/B 已于 2026-09-12 16:34 上线（SPIDER `950b11a`、API `988fee3`/`9e78b9e`，rollout §14）。执行偏差：API v2 valid 直接 `ReportInvalid`（非提前复检）；新索引百度子文档为 0，去 `has_child` 零损失；存量缺失率抽样 0.05%~0.55%，规模远低于 170 万。进度见 `current/tasks.md`。
