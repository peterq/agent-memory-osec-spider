# 记忆系统瘦身与脚本化加载方案

## 背景

记忆仓库运行 10 天后 100 个文件、42 万字。用户 2026-09-12 提出四个痛点：启动即加载的文件过大、索引过大、无关信息占 token、新会话重建上下文找不准。

## 现状诊断（2026-09-12 实测，`scripts/mem/mem.py stat / outline / lint`）

| 项目 | 实测 | AGENTS.md 规定 |
|---|---|---|
| `00-overview.md` | 26,822 字 | ≤ 4,000 字 |
| `01-index.md` | 24,280 字 | 只含导航 |
| `03-project-context.md`（load always） | 2,500 字 | — |
| 启动常驻合计 | 53,639 字 ≈ 4 万 token | — |
| `current/tasks.md` | 58,375 字 | 3,000~6,000 字 |
| 超过 8,000 字的文件 | 8 个 | > 8,000 应拆分 |

体积分布：lessons 23%、sessions 18%、current 15%、knowledge 15%、根目录 4 文件 14%。

根因不是文件多，而是三处**结构性膨胀**：

1. **总览「§2 当前状态」13,228 字**，占总览一半。它把每次会话的完成事项按叙述体追加，实际是 `sessions/` 与 `current/tasks.md` 的第三份复述（改写式复制，逐行去重工具抓不到，`mem.py dup` 只报出 156 字原样重复）。
2. **`01-index.md` 的「关键词索引」200 行**，把「问题 → 文件 + 代码路径」的路由写在索引里，每加一个主题就长一段；同时「文件索引表」98 行是各文件 Front Matter 的手抄本，两者都要人工同步，且 `01-index.md` 自身 `updated_at` 仍停在 09-02。
3. **`current/tasks.md` 是追加式流水账**：09-04 起每个任务块完成后不移出，「已完成」段 + 各任务块历史状态占 90% 以上；真正的未完成项不到 5,000 字。

次要原因：sessions 27 个文件 7.5 万字，`load: on-demand` 但检索时和提炼后的文件同权重竞争，容易被误加载；总览「§6 高价值经验」3,691 字与「§8 快速加载指引」3,034 字是 lessons/procedures 的二次摘要。

## 备选方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. 只做内容整理（人工瘦身总览/索引/tasks） | 无新机制 | 一个月后再次膨胀，索引仍需手工同步 |
| B. 只做向量语义检索 | 问句找得准 | 解决不了常驻文件过大；且专有名词（haisou、res_lc）词法更稳，需与词法融合 |
| C. **索引改脚本生成 + 词法/语义混合检索 + 按需读章节 + 内容瘦身 + 规则收紧**（采纳） | Front Matter 成为唯一需要维护的索引源；启动成本可度量、可 lint 约束 | 需改 AGENTS.md 启动协议；一次性迁移关键词索引 |

## 最终决策（待用户确认后执行）

采纳 C，分四步：

### 第 1 步：工具（已完成，2026-09-12）

`scripts/mem/mem.py`，文档 `scripts/mem/README.md`。子命令 `boot / search / outline / body / lint / stat / dup / recent / embed`，只读。
用户 09-12 同意安装依赖后，检索做成 **jieba BM25 + bge-small-zh 语义的 RRF 融合**（fastembed/ONNX，CPU，模型 ~100MB），语义结果直接给出命中章节。
实测：`boot --kw 4` 输出 13,024 字，可整体替代 24,280 字的索引；7 组自然语言问句（代理池监控没有数字 / 网关重启前要检查什么 / 怎么派子agent才不会重复上下文 / 前端页面样式突然全没了 / 数据库临时表排序规则报错 / haisou为什么下线 / 长时间巡检生产任务有什么坑）Top1 全部命中预期文件；全量建缓存 40 秒，之后每次查询约 1 秒。

### 第 2 步：加载协议改为三层（改 AGENTS.md §4.2 / §5 / §8）

```text
第 0 层 常驻   00-overview.md ≤ 4,000 字（身份 / 当前焦点 ≤5 条 / 核心事实 / 硬约束）
第 1 层 启动包 scripts/mem/mem.py boot（脚本生成，不再手工维护 01-index.md）
第 2 层 按需   mem.py search <关键词> → outline <file> → body <file> --section <标题>
```

`01-index.md` 保留文件名但改为脚本生成物（`boot` 输出落盘），任何 Agent 禁止手工编辑；
「关键词索引」里的「问题 → 文件/代码路径」逐条迁到目标文件 Front Matter 新增字段 `questions:`（触发问题，参与 `boot` 与 `search` 高权重匹配），代码路径迁进目标文件正文。
`lint` 加入会话结束检查清单：常驻文件 > 4,000 字、任何文件 > 8,000 字、悬空引用、`updated_at` 落后于 git，均视为未完成。

### 第 3 步：内容瘦身（一次性，全部为移动而非删除，git 可回溯）

- 总览 §2 只留「最近 7 天重要变化」≤ 5 条、每条 ≤ 2 行 + 指针；历史叙述移入 current/changelog（`load: rarely`，追加式，文件待建）。
- 总览 §6 改为「标题 → lessons 文件」一行一条，≤ 10 条；§8 删除，由 `boot` 承担。
- `current/tasks.md` 只保留未完成/未部署项；已完成块按任务归入 archive/2026/tasks-2026-09（文件待建）。规则：任务「完成且已部署」即移出。
- 超长文件拆分：`patterns-长周期生产巡检`（18k）拆成精简清单 + `knowledge/` 实测数据；`architecture-nc-js`（16k）按「布局/qiankun/网关对接/加页面」拆；`workflow-部署`（12k）拆出「配置 v2 上线」历史段。
- sessions 全部改 `load: rarely`，并写入规则：sessions 只在用户点名「上次那次会话」时读。

### 第 4 步：防复发

- Front Matter 新增可选字段 `valid_until:`（限流/配额类结论有保质期），`lint` 到期提示。
- 会话结束改为「先写详细文件与 Front Matter，再决定总览是否要动」；总览每次改动必须跑 `lint` 通过。
- 可选：Claude Code `SessionStart` hook 自动注入 `boot` 输出；其他 Agent 按协议手动执行。

## 明确不做

- 不引入外部向量库或 API：100~1000 个文件用本地 pickle 缓存 + numpy 点积足够；破千再换 bge-m3。
- 不删除任何历史内容，全部归档可追溯。

## 影响

- 新会话恢复上下文的固定成本从 ≈ 4 万 token 降到 ≈ 1.3 万（overview 4k 字 + boot 13k 字）；后续按需加载每次只读章节。
- 索引维护成本归零；Front Matter 质量成为检索质量的唯一变量。

## 复盘条件

一个月后（2026-10-12）再跑 `mem.py stat`：常驻 > 8,000 字、或 `lint` 出现常驻超长，说明规则未被遵守，需要再收紧。
