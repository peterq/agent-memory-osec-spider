# 决策：跨进程任务投递统一走网关 res_scheduler 队列

## 背景

[事实] 2026-09-04 前，SPIDER 大部分跨进程任务靠 `illuminate/queue-task` 的 `Service`
（`NewService/Dispatch/Serve`，本质是 redis list `service:<name>:queue:task` + pending hash）直连 redis。
生产者与消费者各自拿 redis 连接，网关只是其中一个生产者。缺点：不可观测（没有统一的队列视图/
producer-consumer 记录）、无优先级/去重/超时回收、每个链路各写一套 filter 进程做去重与背压。

[事实] 网关里已有两套队列 RPC：
1. `res_scheduler_rpc`（`services/gateway/res_scheduler/`）：固定队列名 + `TaskPayloadUnion{ResourceTask|KeywordTask}`，
   自带**关键词扇出**（`keywordSubscribed:<site>` + `kwSiteListeners` 注册 + 8h 去重）、`resourcePreCheck` 预检队列、
   账号黑名单 `CheckResourceBeforeCrawl`。2024-08 已用它上线 `v2bndInputPwd`/`v2bndLoadShare`（用户称"已完成改造并上线"）。
2. `gateway_v2`（`SpiderGwV2Rpc`，`services/gateway/spider_gateway/` + `gw_contract.QueueDefine[T]`）：
   通用 namespace/queue/version，任意 payload，有 ListQueue/ListTask，供下载链路(`resDl`/`webResDl`)使用。

## 要解决的问题

把剩余全部 `queue_task.Service` 用法（bnd 老链路、ali/quark/xunlei、6 个关键词站点、keyword_filter、
gateway 的 CommitResource/CommitKeyword/CommitBitTorrent、file_bot、urn）改成网关队列。

## 备选方案

### 方案 A：全部用 `res_scheduler_rpc`（与 v2bnd 同款）
优点：与已上线的参考实现一致；关键词扇出、预检、黑名单钩子都是现成的；payload `ResourceTaskPayload{url,pwd,client,meta,referer}`
足以描述 4 种网盘任务，新增网盘只需在 COMMON 加一个队列名。
缺点：没有 ListTask 之类的观测接口（后续可补）；payload 不通用（磁力/种子放不进去，但磁力已停采）。

### 方案 B：全部用 `gateway_v2` 通用队列
优点：任意 payload、有观测接口、版本管理。
缺点：与 v2bnd 不一致（会出现两套消费模式并存）；关键词扇出/去重要重写；每个站点一个 QueueDefine，
`kwSiteListeners` 这种"在线站点自动订阅"的语义没有对应物。

## 最终决策

**方案 A**。爬虫侧统一模式：
- 消费：`queue_task.StartQueueRemoteConsumer(name, opts, gw_remote_queue.NewResConsumer|NewKeywordConsumer(resCli, q), handler)`
- 生产：`spider_common.NewResLinkCommitter().CommitResLink()` → 网关 `resourcePreCheck`；关键词由网关 `CommitKeyword` 直接扇出
- 网关内置 `resourcePreCheck` 消费者做类型识别、6h 去重（key 含 pwd）、规范化 url、按类型分发到
  `bndInputPwd/bndLoadShare/aliLoadShare/quarkLoadShare/xlLoadShare`，下游 taskKey = 分享 id，目标队列 waiting≥2000 时背压等待。
- 磁力/种子（`CommitBitTorrent`、`services/urn`）不迁移：磁力已停采（见 `decision-2026-09-02-停止磁力资源采集.md`），直接下线。
- STORAGE 的 `save-worker` 也用 COMMON 里同名的 `queue_task.Service`，但那是 STORAGE 进程内部 gateway→worker 的缓冲，
  与 spider 网关无关，**不在本次范围**。
- `devops_check_and_push_clear_queue`（线上 4 台在跑）用的是 `queue_task.Queue2` 直连 redis（不是 list），
  与网关 clear 消费者配套，本次不动，列为后续项。

## 决策原因

用户的参考实现与"已上线"口径都是 res_scheduler；关键词扇出这种最复杂的语义它已经实现好；
统一一种消费模式比"更通用"更重要。观测接口缺口可以后续在 res_scheduler 上补 ListTask。

## 影响

- 新增命令 `v2aliLoadShare`/`v2quarkLoadShare`/`v2xlLoadShare`；删除 `share`/`share_pwd`/`ad_share`/`quark_share`/
  `xunlei_share`/`keyword_filter`/`file_bot`/`urn`；`keyword_*` 命令名不变但改为消费网关队列。
- 上线顺序：先 gateway（新预检分发），再各 v2 消费者与 `keyword_*`，最后删旧容器。切换瞬间旧 redis list 里未消费的任务会丢，
  6h 去重窗口后同一链接可被重新提交，可接受。
- `deploy.sh` 的 `deployService` 只部署 `serviceToCmd` 的第一个词，多命令条目从来没真正生效过（`v2bnd` 条目还写错了名字），已拆成单命令条目。

## 复盘条件

- 需要在网关上观测/管理 res_scheduler 队列（列任务、清队列、改优先级）时，考虑给 res_scheduler 补 ListTask/DelTask RPC，
  或把它迁到 gateway_v2 底座上（两者底层都是 `queue_task.Queue2`，迁移成本主要在 RPC 契约）。
- 出现第 5 种网盘类型：在 COMMON `ResourceQueueNames` 加名字 + 网关预检路由加一行 + 新消费者。
