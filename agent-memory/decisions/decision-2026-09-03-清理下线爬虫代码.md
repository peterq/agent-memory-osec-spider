# 决策：按线上进程清理已下线的爬虫代码

## 背景

SPIDER 仓库积累了多年的爬虫，`spider.go` 注册了 50+ 个命令，其中相当一部分站点早已
下线/改版/收费，代码留在仓库里只造成三种成本：

1. 新人和 Agent 读 `spider.go` 分不清哪些还在跑；
2. `deploy.sh` 的 `serviceToHosts` 里还挂着已经没有进程的服务，误导部署判断；
3. `config.go` / `config*.yaml` 里挂着只有死代码在读的配置节。

`spider.go` 尾部本来就有一段 2023-04-11 的「下线登记」注释，但**只登记不删码**，
三年后这批代码还在。

## 要解决的问题

用一个客观、可复现的判据界定"过期爬虫"，一次性清干净，并且不误删还在生产跑的东西。

## 备选方案

### 方案 A：按 `deploy.sh` 的 `serviceToHosts` 判断

优点：不用连生产。

缺点：**不可靠**。该映射表是人工维护的，本次实测 `aiyoweia` / `repanso` / `yunso_net`
三个服务在表里挂着主机，线上却一个进程都没有。

### 方案 B：以 `./deploy.sh ps` 实测的线上进程为准（采用）

优点：唯一反映现状的判据；只读操作。

缺点：要连 6 台生产机；短暂停机的服务可能被误判（本次涉及的都是停了数月/数年的，无此风险）。

## 最终决策

以 `./deploy.sh ps` 的输出为准，**删除所有线上无进程的站点爬虫代码**，
非爬虫的工具/运维命令（`file_bot`、`urn`、`devops_*`、`dev_add_local_ip_to_qingting`）
即使不在线也**保留**——它们是按需手动跑的。

`keyword_haisou` **保留**（用户明确要求）：当天上线失败，逆向成果有复用价值，
详见 `decision-2026-09-03-下线haisou.md`。

删除清单（21 个命令 / 26,228 行）：

| 命令 | 代码位置 |
|---|---|
| `pansoso` `panduoduo` `sosuopan` `pan56` `xiaobaipan` | `services/{pansoso,panduoduo,sosuopan,pan56,xiaobaipan}/` 整包 |
| `keyword_quzhuanpan` `keyword_pansoso` `keyword_s45256` `keyword_xiaocaizi` `keyword_51caichang` `keyword_51sopan` `keyword_ujuso` `keyword_sopan52` `keyword_aiyoweia` | `services/keyword/*.go` |
| `keyword_magnet` | `services/keyword/magnet-keyword.go`（叠加"磁力已停采"决策） |
| `keyword_repanso` `keyword_yunso_net` | `services/keyword/keyword2024/www.{repanso.com,yunso.net}.go` |
| （无命令入口的死代码） | `services/keyword/keyword2024/ali.gitcafe.ink.go` |
| `keyword_fuck0fy` `keyword_fuck0fy_login` `fuck_gz` `fuck_mall_chat` | `services/keyword/fuck0fy/` 整包 |

连带清理：

- `deploy.sh` 删掉 4 个僵尸服务条目：`aiyoweia` / `repanso` / `yunso_net`（挂着主机但线上零进程）、
  `url_clear`（指向的 `devops_clear_expire_queue` 命令在 `spider.go` 里根本不存在）；
- `config/config.go` 删掉 `Services.{Pansoso,Panduoduo,Xiaobaipan}` 与 `MagnetConfig`；
- `config.prod.yaml` / `config_dev.yaml` 删掉对应的 `pansoso:` / `panduoduo:` / `xiaobaipan:` / `maget:` 节；
- `spider.go` 尾部注释改写成"下线记录（代码已删除，需要恢复请查 git 历史）"，逐条列出删了什么、为什么。

## 决策原因

- 判据客观且可随时复算，不依赖任何人的记忆；
- 代码在 git 里，删除是可逆的，注释里写清了恢复方式；
- 只删爬虫、不删工具，风险面最小。

## 影响

- `spider.go` 命令列表从 50+ 条降到 40 条，剩下的每一条都能在 `./deploy.sh ps` 里找到对应进程
  （唯二例外：`keyword_haisou` 保留待复活、`devops_*` 等手动工具）；
- 第一轮清理时发现的三个遗留问题，用户当场逐条定夺（2026-09-04），已全部处置：
  - ✅ `deploy.sh` 的 `url_clear` 死条目 → 删除；
  - ✅ `services/online_doc/`（金山文档在线文档爬取）、`services/alipan/`（阿里云盘客户端，
    与在跑的 `services/aliyun-drive` 不是同一个包）两个**全仓无引用**的包 → 一并删除；
  - ⏳ 线上 `osec-resdb` 上两个 `spider.go` 已无对应命令的老二进制容器
    （`spider-share_download_push_resolve_alipan_241226` 已跑 20 个月、
    `spider-share_download_push_resolve_qb-250225` 已跑 18 个月）→ 用户确认**不需要了**，
    但 `docker rm -f` 需要 `sudo`（`pplabs` 用户直连 docker.sock 是 permission denied），
    该命令被 Claude Code 自动模式的安全策略拦截，**尚未执行**，命令见 `current/tasks.md`。
- 一个小陷阱：`type Task = keyword.Task` 这个**全包共用的类型别名**当年写在
  `www.repanso.com.go` 里，删该文件会连带打断还在线的 `pansearch_me` / `xuebapan`。
  已提取到新文件 `services/keyword/keyword2024/common.go` 并注明来历。

## 复盘条件

- 某个被删站点重新有价值时 → 从 git 历史取回（`git log --diff-filter=D -- <路径>`），
  但注意这些代码用的是老 `queue_task` 写法，多半不如照 `services/bbs/` 重写。

## 当前状态

代码侧已全部执行完（两轮：先删爬虫，再按用户定夺删死条目与死包）。
`go build ./...` 通过、`go vet` 对改动包零告警、`spider` 二进制可编译且命令列表正确。
**改动已 `git add` 但未提交、未部署**（下次部署任一服务都会重新编译并分发二进制，需留意）。
唯一未完成的动作：osec-resdb 上那两个废弃容器的 `sudo docker rm -f`（见上）。
